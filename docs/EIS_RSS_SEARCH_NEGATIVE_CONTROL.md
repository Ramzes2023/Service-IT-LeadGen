# Контрольная проверка поисковых фильтров RSS ЕИС — 31 октября 2026

## Почему понадобилась

В реальной проверке Windows выполнено **67 pass**, `OFFICIAL_FEED_PARSED`, получено **200** извещений из пробной RSS по `searchString=1С` и `fz44=on`. Результат: **181** закупка без «1С» в распознанном предмете, **19** без распознанного поля предмета, 0 исследовательских кандидатов. У части записей очевидно посторонние медицинские услуги или оборудование. Это может указывать на неработающий или слишком широкий фильтр в пробной ссылке, но по одному ответу ЕИС **не доказано**.

## Новая read-only проверка

`leadpilot.eis_search_integrity` принимает безопасный сохранённый JSON предыдущей удачной проверки `eis_scope_*.json` и выполняет ровно **два GET** к официальному `https://zakupki.gov.ru/epz/order/extendedsearch/rss.html`:

1. запрос с **теми же фильтрами**, что были в сохранённом отчёте;
2. запрос, где изменён **только существующий параметр** `searchString` на диагностический код, не встречающийся в реальных закупках. Остальные параметры `fz44`, фильтры региона и др. не меняются.

Парсер формирует SHA-256 множества официальных URL **всех извещений**, в том числе нецелевых, не сохраняя их открытым текстом в диагностике. Далее сравнение:

- `NEGATIVE_CONTROL_IDENTICAL_NOTICE_SET_SEARCH_UNTRUSTED`: у исходного и невозможного слова одинаковые минимум 10 официальных URL. Это **серьёзный признак**, что фильтр слова не применяется или ответ закеширован/некорректен. **Не доказывает** конкретную внутреннюю причину, но запрещает полагаться на эту RSS-ссылку для целевого поиска.
- `NEGATIVE_CONTROL_EMPTY_SEARCH_MAY_BE_APPLIED`: по невозможному слову 0 извещений; изменение поискового слова влияет на результат, но ещё надо доказать корректность реальных параметров запроса.
- `NEGATIVE_CONTROL_DIFFERENT_NOTICE_SETS_NOT_PROOF_OF_SCOPE`: множества разные; это ещё не подтверждает 1С, Москва/МО или ФНС.
- `INCONCLUSIVE_...`: данных недостаточно.

Проверка не отключает TLS, не следует редиректам, не повторяет ошибки/429, не обходит защиту. Два разрешённых запроса к публичной RSS — без учётных данных, без CRM, без рассылок. В логах нет поисковой строки, URL элементов или персональных контактов.

Одновременно `leadpilot.eis_source_diagnostics --show-public-samples` выводит **восьмистрочный максимум** образцов публичных названий закупок в ASCII-экранированном формате. Если `????` исчезнет и появится `\\u041e` и т.п., проблема была в Windows консоли. Если сами названия хранятся в JSON как `????`, надо отдельно проверить реальную XML-кодировку; нельзя менять критерий фильтра на основании повреждённого текста.

## Windows запуск

Разработан пакет `ServiceIT_EIS_SEARCH_CONTROL_20261031.zip`: pinned SHA `ed680abcd3e3b42557da2af584686f0c9e46760e`. Он автоматически использует предыдущий локальный JSON и существующий Python .venv из репозитория; создаёт detached worktree, запускает EIS-тесты и контрольные два запроса. Код **ещё не выполнялся на Windows**, поэтому предыдущее 67 pass относится только к предыдущему коммиту.

## Что не допускается

Не считать ЕИС 44-ФЗ государственные закупки подтверждённым спросом **микро/малого коммерческого покупателя Москвы/МО**. Даже найденная закупка услуг 1С требует проверки оригинала, срока подачи, юридического ИНН **покупателя** и ФНС, контакта, дублей, стоп-листа и решения менеджера. `qualified_leads=0` и `crm_writes=NO` сохраняются. Битрикс24 и VALYQON не затрагиваются.
