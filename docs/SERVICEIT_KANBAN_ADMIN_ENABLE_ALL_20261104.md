# Сервис ИТ — автоматическое оформление новых карточек для общего Канбана

**Цель:** после однократной настройки Канбана администратором сотрудникам показывается единый заголовок каждой новой карточки смарт-процесса `1062/21`, без ручного оформления при каждом поступлении.

## Что подключено в worker

- 📑 `ТЕНДЕР · <краткое название>`;
- 👥 `ВАКАНСИЯ · <краткое название>`;
- 🎯 `ПРЯМАЯ УСЛУГА · <краткое название>`;
- ⚪ `УТОЧНИТЬ ТИП · <краткое название>` для неоднозначных/неразрешённых типов.

Общий helper: `serviceit_kanban_tile.tile_heading_for_signal`. В действующих `preliminary_fields` и `hold_analysis_fields` заголовок становится **первой строкой** существующего поля `UF_CRM_13_SVCIT_AI_SUMMARY`, далее статус HOLD/ручная проверка. В подтверждённом `verified_fields`/GigaChat пути такой же заголовок включён перед `🟢/🟡/🔴 Score`, но score берётся исключительно из уже авторизованного независимого скоринга. Вариант `🎯 ПРЯМАЯ УСЛУГА` — только текстовое отображение; старое техническое обозначение `🎯 ЗАПРОС УСЛУГ` в классификаторе/черновиках задач остаётся совместимым.

Фиксированный существующий write allowlist — **9 AI-полей** для HOLD или **9 AI + 3 Score** для реально проверенных карточек. НЕТ отдельных обновлений названий, стадий, старых карточек, Битрикс-настроек, задач, источников или SEO. Source-created B2B-тендеры уже имеют префикс в `title`; чужой `title` этим изменением не переписывается. Для вакансии/прямой услуги знак появляется через `AI_SUMMARY` после штатной обработки новой карточки.

## Один раз делает администратор Bitrix24

1. Зайти в `Сервис ИТ — AI-сигналы` (`entityTypeId=1062`, `categoryId=21`) под своим аккаунтом **администратора Битрикс24 или CRM**.
2. На странице Канбан открыть `Настройка канбана → Настроить карточку просмотра` или `Быстрый элемент → Выбрать поле → Настройка полей для просмотра карточки` (меню может отличаться).
3. Включить **для всех сотрудников** поля: `Название`, `AI — краткий вывод` (код `UF_CRM_13_SVCIT_AI_SUMMARY`), `AI — статус` (`...AI_STATUS`), `AI — цветной приоритет` (`UF_CRM_13_SVCIT_AI_SCORE_BADGE`), `Lead Score` (`UF_CRM_13_SVCIT_LEAD_SCORE`) по возможности, `Направление услуги` (`...SUGGESTED_SERVICE`). При ограничении числа полей сохранить в приоритете `AI_SUMMARY` и `AI_SCORE_BADGE` (последнее может быть пустым у HOLD).
4. Проверить поле `AI_SUMMARY` в реальном браузере у **двух сотрудников**. Некоторые типы длинных пользовательских полей/личные overrides могут не отображаться в предварительной плитке; в этом случае применить допустимое поле или ограничение UI, а не считать настройку успешной из-за REST кода.
5. Для разделов **внутри** полной карточки — отдельно согласовать `crm.item.details.configuration.set(scope=C)` (полный backup перед заменой). Текущий вебхук пользователя 1615 **не администратор**, поэтому эта операция заблокирована.

## Важные ограничения

- Это **НЕ** включение промышленного verified Lead Score. Live Stage4 writer остаётся выключенным до подтверждённых 9 корпоративных gate proofs ФНС/CRM/STOP/право контакта/и др. Для HOLD не подставлять `0`, `65`, `90` или любой фиктивный Score.
- Один раз настроенный общий Канбан показывает поля **всех новых поступлений, уже обработанных действующим worker**; но нельзя обещать мгновенное появление текста до завершения GitHub cron/event. GitHub расписание best-effort.
- Событие/график обработки должен реально найти новую карточку, выполнить точный `crm.item.update` и `crm.item.get` readback. До такой первой проверки объявлять полный live-E2E нельзя.
- Исторические `#3` и `#7`, основной техподдержка pipeline и другие источники не затрагиваются.
