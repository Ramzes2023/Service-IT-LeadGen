# Сервис ИТ — маршрутизация трёх типов сигналов (MVP v1)

**Основание:** письмо Микаила «ТЗ Лидогенерация», приложение «ТЗ_система_лидогенерации_Сервис_ИТ_итоговое.docx», версия 3.0. Приоритет: Москва/МО, небольшие компании и сопровождение 1С, далее Ингушетия. Дополнительные услуги: IT-аутсорсинг, ККТ и маркировка, торговое оборудование, 1С/Битрикс24, ЭДО/ЭП/КриптоПро, серверы/сети, интеграции и ИИ.

## Данные, источник правды и приоритет

Для каждой новой карточки CRM 1062/21 `leadpilot.serviceit_three_signal_triage` определяет **тип** и *ориентировочный приоритет проверки*. Он не назначает итоговый Lead Score. Это принципиально: итоговая оценка 0–100 назначается только после версионированной детерминированной схемы и независимых корпоративных проверок ФНС/ИНН, CRM-дублей, действующего клиента, стоп-листа, правового основания контакта, региона, услуги и источника. GigaChat может предложить гипотезу по разрешённому **публичному названию** тендера или вакансии, но не может подтвердить реальный спрос, срок и контакт; коммерческое решение принимает менеджер.

Поля `AI_SUMMARY`, `AI_MANAGER_BRIEF`, `AI_FULL_REPORT`, `AI_NEXT_ACTION`, `AI_RECOMMENDATION` получают читаемые типовые сведения в рамках *существующего разрешённого набора ровно девяти полей*; `crm.item.update` для иных полей в этом обработчике запрещён. B2B-Center создаёт новые карточки уже с префиксом **📑 ТЕНДЕР** в `title` — виден на Канбане ещё до открытия. Для вакансии и прямого запроса эмодзи стоит в `AI_SUMMARY`. Он будет виден до открытия только при размещении этого поля в отображении Канбана: это **настройка UI Битрикс24, пока не подтверждена**. Подменять название/этап уже созданных карточек без отдельного разрешения нельзя.

Контакт (корпоративный номер, публичная корпоративная почта) допускается в отчёт **только** с датой последней проверки (не старее 30 дней) и URL официального сайта компании. Модуль принимает эти данные только от отдельного доверенного обработчика источника. Он **не выполняет автоматический поиск сайтов и телефонов**, не угадывает адреса, ЛПР и личные контакты. Данные из произвольной карточки CRM или из свободного ответа модели не делают контакт «проверенным».

Аналогично, публикация, открытость вакансии/закупки, дата и дедлайн считаются подтверждёнными только от отдельно проверенного актуального источника (не старее 72 часов). Просроченный тендер не получает срочное задание; действующий тендер с проверенным сроком — внутренний крайний срок задачи до завершения подачи заявок.

## Задачи менеджеру — текущий статус

Функция `task_draft` готовит содержательное **предложение внутренней задачи** с типом сигнала, следующим действием, сроком (где подтверждён), ссылкой на CRM и требованием проверить дубли/STOP. **Фактический вызов `tasks.task.add` НЕ включён**: запрещено угадывать ID корпоративного менеджера, права и параметры привязки к процессу или создавать повторные задачи. Для этого есть новая read-only проверка `leadpilot.serviceit_manager_task_scope_probe`, доступная через owner-only маркер `SERVICEIT_MANAGER_TASK_SCOPE_READONLY_V1` в issue #74. Она проверяет реальный task scope, `UF_CRM_TASK`, привязку к процессу и owner type symbol. Для включения создания нужны дополнительно точное подтверждение ID ответственного, проверка дубликатов задач, разрешение на `tasks.task.add`, журнал однократной записи и независимый readback.

## Границы безопасности и оставшиеся пункты до полного MVP

1. Отдельный адаптер получения содержимого **официального первоисточника**, времени и условий по каждому типу (не текст из произвольного письма).
2. Проверяемое обогащение компанией и корпоративными контактами с URL/датой и разрешёнными запросами; фильтр действующих клиентов и стоп-лист.
3. Версионированный *формальный* Lead Score после независимых gate-условий, а не свободная оценка GigaChat.
4. Реальное создание задач менеджера только после read-only проверки прав, привязки и ID менеджера, затем точный однократный canary.
5. Отображение поля `AI_SUMMARY` в Канбане для вакансий и прямых заявок с подтверждением корпоративного UI, без замены существующих секций.
6. Конечная проверка новой реальной карточки: источник → тип и эмодзи → публичные данные и GigaChat-гипотеза (если разрешена) → девять полей с exact readback → одна задача нужному менеджеру; **этого сквозного подтверждения пока нет**.

Тесты в `tests/test_serviceit_three_signal_triage.py`, `tests/test_serviceit_b2b_hold_ai_fields.py`, `tests/test_serviceit_manager_task_scope_probe.py`. В production source→CRM и worker gate изменения до отдельного приёмочного proof не отключают защиту старых карт и не выполняют массовые рассылки/звонки.
