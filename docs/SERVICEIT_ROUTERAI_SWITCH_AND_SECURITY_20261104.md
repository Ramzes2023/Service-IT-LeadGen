# Подключение RouterAI к новым карточкам Сервис ИТ

Сервис из сообщения WhatsApp: routerai.ru, базовый URL https://routerai.ru/api/v1. Ранее упомянутый DeepSeek является моделью через маршрутизатор, а не прямым адресом API.

Провайдер конфигурации: routerai. Модель: deepseek/deepseek-v4.1-flash. Адрес запросов: https://routerai.ru/api/v1/chat/completions. Резервный вариант: gigachat.

Ключ, отправленный на скриншоте WhatsApp, раскрыт — его необходимо отозвать в кабинете RouterAI и выпустить новый. Никогда не публиковать его в Issue, коммитах и чате.

Владелец GitHub один раз добавляет новый ключ в Settings > Secrets and variables > Actions: секрет SERVICEIT_ROUTERAI_API_KEY. После решения руководителя о разрешённой передаче корпоративных данных RouterAI: переменная SERVICEIT_ROUTERAI_PRIVACY_APPROVED со значением YES_1062_21. Затем переменная SERVICEIT_AI_PROVIDER = routerai.

Для возврата: SERVICEIT_AI_PROVIDER = gigachat. При отсутствии переменной выбирается GigaChat. Новая интеграция не меняет уже обработанные карточки, фактический Score, проверки ФНС и CRM-дублей, Kanban или текущую воронку техподдержки.

Без нового действительного ключа и отдельного разрешения реальный RouterAI API тест и переключение запрещены. Покупка ключа не равна разрешению передачи внутренних данных.

Базовый AI-режим отправляет ограниченный текст публичного заголовка только после проверки домена источника и разрешения. Для внутренних документов/CRM данных требуются корпоративные approvals. Модель возвращает гипотезу, цитату и направление услуги, а не подтверждённый лид или конечный Lead Score.

Справка: https://routerai.ru/docs/guides/overview/quickstart ; https://routerai.ru/models/deepseek/deepseek-v4.1-flash

## Реальная проверка 04.11.2026 и новая защита от поломки

Новый ключ (значение скрыто) обнаружен GitHub Actions; переменные `SERVICEIT_AI_PROVIDER=routerai` и `SERVICEIT_ROUTERAI_PRIVACY_APPROVED=YES_1062_21` были сохранены владельцем. Публичный тест без данных клиентов:
- #41918392498: отказ `401/403` при платном запросе.
- #41918947336: каталог моделей `GET /models` HTTP 200, но `POST /chat/completions` HTTP 401.
- #41919599689: статус `ROUTERAI_CHAT_401_WITH_CREDITS_UNVERIFIED`. Баланс программно подтвердить не удалось. **Не утверждать, что денег нет или ключ неправильный**.

**Безопасность продакшена:** новый переключатель `SERVICEIT_ROUTERAI_LIVE_READY` должен быть точно `YES_API_CHECK_PASSED`; если отсутствует или иначе настроен, оба основных облачных workflow временно выбирают GigaChat и сохраняют его отдельный TLS CA сертификат, даже если `SERVICEIT_AI_PROVIDER=routerai`. Это предотвращает отказ обработки новых карточек при неисправном платном API. Настройку READY можно устанавливать только после повторного успешного синтетического API теста `ROUTERAI_API_AND_AI_VALIDATION_PASS` под действительным ключом.

Что нужно сделать владельцу аккаунта RouterAI: открыть Биллинг, проверить положительный остаток и лимиты ключа на платные запросы, проверить разрешённость модели. Если аккаунт пополнен, а `POST /chat/completions` возвращает 401 при рабочем `GET /models`, обратиться в поддержку RouterAI с датой и кодом 401 **без передачи API ключа**. После устранения проблемы повторить проверку; только потом добавить переменную `SERVICEIT_ROUTERAI_LIVE_READY=YES_API_CHECK_PASSED`. Не ставить её сейчас.

GitHub Secrets не нужно переписывать без подтверждённой причины. Изменения не затрагивают исторические CRM карточки, Score, источники и менеджерские задачи.


## Углублённая диагностика — 05.11.2026 (обновление по двум операционным системам)

**Важная поправка к историческому утверждению про `GET /models`:** публичный каталог возвращает HTTP 200 **без Authorization** и с Authorization. Поэтому `GET /models=200` **не подтверждает** действительность API-токена. `GET /credits` выдаёт HTTP 401 и, согласно RouterAI, управление ключами/учётные операции могут требовать отдельного master/management credential. Не выдавать отказ `/credits` за нулевой баланс.

Проверены факты с реальными GitHub Actions, без раскрытия секрета:
- [#42030067992](https://github.com/Ramzes2023/Service-IT-LeadGen/actions/runs/42030067992): DNS IPv4 OK, главная RouterAI 200, docs 200, anonymous models 200, authorized models 200, credits 401; в GitHub runner нет переменных `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY`, `trust_env=False` и `True` дают **те же ответы**. Временные 502 на 05.11 были, но не сохраняются как причина каждого 401.
- [#42030821507](https://github.com/Ramzes2023/Service-IT-LeadGen/actions/runs/42030821507): минимальный POST `chat/completions`, **без** `response_format` и tools, `max_tokens=8`, на Ubuntu и Windows даёт **401 с существующим ключом И 401 без ключа**. Не работал даже минимальный формат, следовательно JSON mode не объясняет отказ. Отпечаток ключа: присутствует, не содержит `Bearer `, кавычек/пробелов/переводов строк, но **НЕ начинается с `sk-`**. Само значение нигде не выводилось.
- У RouterAI в публичных инструкциях о подключении API-ключи для вызова моделей указаны в формате `sk-...`. В отдельной документации разделены **обычный API-ключ для /chat/completions** и **master key для администрирования /keys**. Поэтому самая вероятная причина — в секрет GitHub `SERVICEIT_ROUTERAI_API_KEY` внесён **не токен inference API от нужного аккаунта**, а иной вид ключа/идентификатор/старый отозванный токен. Невозможно по одному префиксу доказать, какой именно токен там записан.
- 1000 ₽, о которых сообщил Михаил, могли быть зачислены в аккаунт, но **баланс программно не подтверждён**; данные `GET /credits` не доказывают обратного. Пополнение не исправляет ошибочный токен.

**Исправление со стороны интеграции:** провайдер RouterAI теперь проверяет ключ на соответствие описанному формату **офлайн и без платных вызовов**. Неверный/сомнительный формат возвращает `ROUTERAI_API_KEY_FORMAT_INVALID_NO_NETWORK` в synthetic preflight и отклоняется в провайдере без отправки данных. Ни один флаг RouterAI READY от этого автоматически не включается; GigaChat остаётся резервом.

**Что необходимо только от владельца кабинета RouterAI (Михаила):**
1. Войти в `routerai.ru` под **тем же аккаунтом, где было пополнение**; посмотреть баланс и статус платёжной операции.
2. Открыть **Настройки → API-ключи**, а не «Мастер-ключи». Выбрать нужный токен именно для **моделей**; прежний, показанный на скриншоте, перевыпустить/отозвать. Проверить, что новый токен начинается на `sk-`, он показан в кабинете, а не является названием/ID ключа.
3. Сразу обновить **GitHub Settings → Secrets and variables → Actions → Repository secrets → `SERVICEIT_ROUTERAI_API_KEY`**. Вставить только токен, **без** `Bearer`, кавычек и пробелов. Не присылать его сюда, Михаилу в незашифрованный чат, в Issue или в коммит.
4. Дальше владелец запускает owner-only `SERVICEIT_ROUTERAI_SYNTHETIC_PREFLIGHT_ONCE_V1` в Issue #148. Только после **`ROUTERAI_API_AND_AI_VALIDATION_PASS`** разрешено устанавливать `SERVICEIT_ROUTERAI_LIVE_READY=YES_API_CHECK_PASSED` и проводить новую readback проверку на **будущей** реальной карточке. До этого GigaChat остаётся активным и никаких повторов на старых карточках.

Официальные справки: https://routerai.ru/docs/guides/overview/authentication и https://routerai.ru/pages/bench-routerai . Если правильный новый `sk-` токен после этого снова возвращает 401, открыть тикет в RouterAI support@routerai.ru с UTC-временем, минимальным endpoint, статусом, названием модели и сведениями из кабинета; **без ключа**, с указанным платёжным аккаунтом. Проверить связку аккаунт ↔ ключ ↔ баланс и возможные лимиты/IP restrictions уже у провайдера.
