# Тестовая задача менеджера, связанная с карточкой ServiceIT №3

**Статус:** строгая предварительная сборка задания, **без выполнения REST-записи**.
Последняя подтверждённая живая DEMO-карточка: [№3](https://serviseit.bitrix24.ru/crm/type/1062/details/3/), `DEMO-ITREQ-001`, smart process 1062 / category 21, стадия `DT1062_21:CLIENT`. Другие реальные CRM-объекты и поддержка не затрагиваются.

## Зачем отдельная задача

ТЗ Михаила (версия 3.0, разделы 7–9) предусматривает не только найденный B2B-сигнал в CRM, но и отдельное действие для ответственного менеджера. На снимке карточки справа было стандартное предложение «Создайте дело» — **не подтверждение**, что задача уже создана.

По [официальному Bitrix24 туториалу](https://apidocs.bitrix24.ru/tutorials/tasks/how-to-connect-task-to-spa.html) для `tasks.task.add` с привязкой `UF_CRM_TASK` к смарт-процессу нужны одновременно:

1. Результат `crm.enum.ownertype`: проверить `ID=1062` и `SYMBOL_CODE_SHORT`; **не подставлять произвольный код**. Теоретический короткий код `T426` (1062 = 0x426) должен совпасть с REST.
2. `crm.type.get`: `isUseInUserfieldEnabled=Y` и `linkedUserFields["TASKS_TASK|UF_CRM_TASK"]="true"`, причём **обе настройки необходимы**. Не менять настройки типа без согласия администратора.
3. `crm.item.get`: полная проверка точного `id=3`, `entityTypeId=1062`, `categoryId=21`, `stageId=DT1062_21:CLIENT`, заголовка `DEMO-ITREQ-001`, уникального DEMO-ключа, всех 16 исходных UF-полей, `example.invalid` и отсутствия реальных привязанных контактов.
4. `tasks.task.getFields`: подтвердить `TITLE`, `RESPONSIBLE_ID`, а также `UF_CRM_TASK` с типом `crm`.
5. `user.get`/другой корпоративный допустимый read-only способ: получить **реальный ID активного сотрудника** для `RESPONSIBLE_ID`. Нельзя считать, что владелец вебхука — Михаил. Устанавливает и подтверждает соответствие корпоративный администратор/Михаил.
6. Независимое разрешение на одну учебную задачу, проверка отсутствия ранее созданной задачи по DEMO-ключу/CRM-привязке, защищённая локальная транзакционная очередь, неопределённое состояние POST без слепого повторения, `tasks.task.get` с выборкой `UF_CRM_TASK` и проверка результата. Никакие автоматические письма, звонки, сообщения не допускаются.

**Важно:** задачи Bitrix24 и CRM-дела — разные механизмы. `tasks.task.add` создаёт задачу сотрудника, а `crm.activity.todo.add` — дело CRM. Их нельзя выдавать одно за другое. В текущем PR обе реальные операции отключены.

## Что реализовано в этом PR

`leadpilot/bitrix_1062_manager_task_preview.py` принимает **уже прочитанные** метаданные и карточку и выдаёт только `method_if_separately_authorized="tasks.task.add"`, `params_not_sent.fields` с `UF_CRM_TASK=["T426_3"]` (только после проверенного owner-type) и подтверждённым техническим ID исполнителя. Текст задачи однозначно учебный: «НЕ ЗВОНИТЬ / НЕ ПИСАТЬ». Права пользователя Михаила **не утверждаются** автоматически.

Тесты `tests/test_bitrix_1062_manager_task_preview.py` проверяют неверные карточки, смену стадии, отсутствие 16 исходных UF-полей, связанные реальные компании/контакты, неподходящего исполнителя, отсутствие разрешения связки, robots/bizproc, несовпадение owner-type, ошибку схемы задач и отсутствие сети.

Полный автономный Windows runner:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/RUN_SERVICEIT_LINKED_TASK_ACCEPTANCE.ps1
```

Он **не запрашивает вебхук**, выполняет syntax, целевые и полные pytest проверки; никаких записей в Bitrix24.
