# ServiceIT — исправление проверки владельца вебхука после live-блокировки

## Фактический инцидент

Владелец запустил `RUN_SERVICEIT_AUTO_OWNER_ONE_DEMO_TASK.ps1` на коммите `50669142cfd2e94b5ebfe14c8aa062f9be795d3a`. Итог:

```text
SERVICEIT_AUTO_SELF_DEMO_TASK=START
OWNER_ID=READ_FROM_PORTAL_PROFILE; NO_ID_ENTRY=YES
SERVICEIT_AUTO_TASK=BLOCKED_OR_UNCERTAIN;OWNER_IDENTITY_UNVERIFIABLE
SERVICEIT_AUTO_SELF_DEMO_TASK=BLOCKED_OR_UNCERTAIN
```

Строгая проверка прервала запуск **перед вызовами `tasks.task.list` и `tasks.task.add`**: совпадение ID пользователя из `profile` с владельцем URL проходило, но одновременно требовались непустые `NAME` и `LAST_NAME`. Фактическая причина — *по крайней мере одно поле имени не удовлетворило требованию*, а не доказанное отсутствие именно фамилии. **Живая задача не подтверждена**.

## Точечное исправление

В `leadpilot/bitrix_1062_auto_owner_demo_task.py` фамилия стала необязательной (может быть `None` или пустой строкой). По-прежнему обязательны:

- ID из `profile` — положительное число, **в точности совпадает с ID пользователя в URL того же самого разрешённого вебхука**;
- непустое имя длиной 2–80 символов;
- если фамилия есть — она должна быть корректной строкой;
- имя/фамилия не должны совпадать с Михаил / Микаил / Миша / Mikhail / Michael и ограниченным набором очевидных транслитераций;
- все прежние CRM identity, metadata и task duplicate preflight;
- тот же локальный `%LOCALAPPDATA%\ServiceIT\One-Demo-Manager-Task\one-demo-task.sqlite3` и запрет повторного POST.

Если имя отсутствует, появляется отдельный статус `OWNER_FIRST_NAME_MISSING`; если неверный тип фамилии — `OWNER_SURNAME_INVALID`. Не печатаем реальные имя, ID, вебхук или чужие данные.

Модуль не создаёт задачу сам по себе; реальная операция возможна только при явном запуске оператором `RUN_SERVICEIT_AUTO_OWNER_ONE_DEMO_TASK.ps1`. Она может уведомить **сотрудника-владельца вебхука** внутри Bitrix24. Поэтому использовать только корпоративно разрешённый webhook для тестовых задач, не webhook сотрудника, которого нельзя беспокоить.

**Никаких CRM-записей, внешних клиентов, источников закупок, писем, звонков и дополнительных задач изменение кода не выполняет.**

## Контроль качества

Добавлены mock-тесты для отсутствующей фамилии, пустой фамилии, отсутствующего имени, запретного получателя и неправильного типа данных. До повторного запуска требуется зелёный CI. Локальная SQLite-резервация при прежней ошибке не должна была создаваться, поскольку вызов выполнялся до дедупликации и создания; однако перед повторным операторским запуском желательно убедиться, что нет исторической строки `UNCERTAIN_POST_RESERVED` от другого запуска.

Официальный `profile`: https://apidocs.bitrix24.ru/api-reference/common/users/profile.html .
