# Сервис ИТ — автоматический расчёт прибыли 15/10/75 с ручным дополнением менеджером
Дата: 05.11.2026. Новая интеграция только для **реально успешных новых сделок** отдельной воронки «Лидогенерация» (CRM entityTypeId=2; дата создания после 05.11.2026 00:00 UTC). Техническую поддержку, исторические сделки, старые карточки 1062/21, источники и банковские платежи не меняет.

## Правило, уже согласованное компанией по словам владельца

После реально оплаченной выручки **без НДС** и прямых расходов РВП распределяется так: **15% разработчику, 10% менеджеру, который осуществил продажу, оставшаяся сумма компании** (75% при положительной РВП). Если РВП отрицательная или 0, обе премии равны нулю; отрицательный остаток несёт компания. Пример: оплачено 5 000 ₽ без НДС, прямые расходы 1 000 ₽: РВП 4 000 ₽, разработчик 600 ₽, менеджер 400 ₽, компания 3 000 ₽.

Повторно согласовывать **проценты** не нужно. Но данные из комментариев менеджера не являются банковским подтверждением и не дают права перечислять деньги/начислять зарплату.

## Как система автоматически работает при наличии подтверждённых данных

1. GitHub Actions `serviceit-finance-hybrid-live.yml` проверяет CRM каждые 30 минут в облаке (GitHub cron — best effort). Параллельно можно запустить однократно через Issue #148: `SERVICEIT_FINANCE_HYBRID_LIVE_ONCE_V1`.
2. Прежде всего находит ровно одну *видимую по текущим правам* воронку **«Лидогенерация»**. Если её пока нет или она не видна, итог `FINANCE_LEADGEN_FUNNEL_NOT_VISIBLE_NO_WRITE`; **никаких** задач в техподдержке.
3. Только новые успешные сделки (`STAGE_SEMANTIC_ID=S`, `CATEGORY_ID` точно соответствует этой воронке, `CURRENCY_ID=RUB`, `DATE_CREATE` после даты запуска), с реально назначенным активным сотрудником.
4. В первую очередь использует **только точные специализированные финансовые поля** сделки (если они существуют): `UF_CRM_SVCIT_FIN_PAID_EX_VAT`, `UF_CRM_SVCIT_FIN_DIRECT_COSTS`, `UF_CRM_SVCIT_FIN_PAYMENT_DOC`, `UF_CRM_SVCIT_FIN_COST_DOC`. **Никогда** не считает стандартное `OPPORTUNITY` подтверждённой оплатой. Эти поля могут отсутствовать без админ-настройки — это нормально, их отсутствие приводит к ручному вводу.
5. Когда суммы отсутствуют, создаёт **одну** внутреннюю задачу Битрикс24 для ответственного менеджера, связанную с той же сделкой через `UF_CRM_TASK=["D_<id>"]`. Она не звонит и не пишет клиенту.
6. Менеджер заполняет недостающую информацию в поле **«Комментарии» самой сделки**, аккуратно добавляя блок ниже в конец. Не удалять существующие комментарии. Если в Bitrix есть профессиональные финансовые поля, можно заполнить их вместо блока, если администратор настроил их кодами из п. 4.
7. На следующем запуске система читает данные и **автоматически считает 15/10/75**. Результат создаёт как *отдельную внутреннюю связанную задачу* для менеджера; если менеджер изменяет числа, обновляет описание собственного отчётного задания, а не старые сделки или пользовательские комментарии.
8. Если CRM и менеджер указали разные суммы — `FINANCE_VALUES_CONFLICT_MANAGER_REVIEW`, расчёта нет, нужен разбор. Если значение расхода не заполнено, его **нельзя** заменить нулём. Явно указанный `0` допустим. При исчезновении данных прежние суммы в расчётной задаче должны стать `СТОП`.
9. Если сумма есть, но нет документа — формирует предварительный расчёт, одновременно запрашивает недостающие документальные реквизиты. **Любые суммы в менеджерских комментариях предварительные**. Бухгалтерия должна сверить поступление на банковском счёте, исключение НДС и документы расходов. Выплаты никогда не запускаются из этого workflow.

## Что написать менеджеру в Битрикс24

В поле `Комментарии` **реальной успешно завершённой сделки в отдельной воронке**, в конце существующего содержимого добавьте:

```text
SERVICEIT_FINANCE_V1_BEGIN
PAID_EX_VAT_RUB=5000.00
DIRECT_COSTS_RUB=1000.00
PAYMENT_DOCUMENT=bank:10001
COST_DOCUMENT=act:10001
SERVICEIT_FINANCE_V1_END
```

Числа и номера выше — только **поясняющий образец**, не реальные платежи. Не копируйте их в реальную сделку без подтверждения. Система требует десятичную точку, рубли и фактически оплаченные суммы без НДС. Документы можно оставить пустыми, но это останется предварительным расчётом. Добавлять только один блок. Для HTML-редактора используйте обычный текст: если Bitrix обернёт строки в HTML, парсер остановится для проверки, а не будет угадывать значения.

Результат записывается в отдельную **внутреннюю задачу** Битрикс24; во внешние письма, CRM сделки/клиентов, GitHub комментарии, GitHub Step Summary **денежные значения не записываются**.

## Незавершённые условия и причины

- Сейчас у штатного webhook нет CRM-admin. Корпоративный запуск ранее показал `CRM_ADMIN_REQUIRED_NO_WRITE`; отдельная воронка **ещё не создана**. До её появления новые финансовые задачи **не создаются** (это строгая защита).
- Существование подходящих финансовых полей не доказано до read-only аудита `SERVICEIT_FINANCE_SCHEMA_READONLY_ONCE_V1` через Issue #148. Аудит не читает персональные платежи.
- При наличии другой валюты (EUR и др.) модель не пересчитывает в RUB без проверенного курса: такая сделка остаётся заблокированной.
- Для реальных официальных начислений нужна бухгалтерская проверка документов и внешнего банковского источника (этого подключения пока нет). Проценты уже согласованы по заявлению владельца; именно **источник достоверных оплат/расходов**, а не повторное согласование 15/10/75, остаётся незакрытым.
- Факт наличия реальной успешно закрытой **новой** сделки пока не подтверждён: нельзя выдавать CI mock-тест за работу на настоящей продаже.
- Если роль ответственного менеджера не видна, задача не создаётся. При недоступности task REST или GitHub зашифрованного ledger — fail-closed, без повтора потенциально созданной задачи.

## Безопасность и ограничение прав

Workflow пишет **только** `tasks.task.add` и `tasks.task.update` для своих внутренних задач в подтверждённой отдельной сделке. Методы `crm.deal.update`, `crm.item.update`, `crm.category.add`, `crm.deal.add` запрещены. Два одноразовых пути и отдельные версии отчёта в шифрованном ledger GitHub защищают от дублирования при повторных/неоднозначных ответах REST. Операция назначения сотрудника проверяет его активный корпоративный статус; отчёт нельзя обновить, если это не наша собственная задача, созданная текущим webhook.

Официальные методы REST: `crm.deal.list/get/fields`, `crm.category.list`, `tasks.task.getFields/list/add/get/update`, `user.current/user.get`. Внешние финансовые и банковские API не вызываются.
