# Исправление цветного индикатора после подтверждённого пустого поля

**Дата:** 02.11.2026. **Состояние:** исходная операция badge:1062:21:3:v1 = UNCERTAIN, создание поля = VERIFIED, обе версии поля в живом `crm.item.get` (useOriginalUfNames Y/N) возвращают EMPTY. Lead Score 90 и GigaChat-отчёт сохранены. Из этого невозможно точно определить причину: исходный `crm.item.update` мог быть проигнорирован, например из-за поля или внутренней нормализации.

**Ограничение:** команда из PR #62 с `-ApplyDemo` **навсегда запрещена к повтору**. Не удалять журналы/бэкапы, не менять StateDir ради обхода защиты.

## Новый контракт — отдельная, согласованная операция

Оператор `scripts/RUN_SERVICEIT_KANBAN_BADGE_RECONCILIATION.ps1`. Корпоративный webhook через проверенный `Read-Host -AsSecureString`.

- Без ключей — полностью офлайн (0 CRM writes).
- `-InspectLive` — исключительно GET, проверка оригинального журнала (старое поле VERIFIED и старая запись UNCERTAIN), обеих пустых версий поля, неизменного DEMO id=3, score 90/100, версии, существующего GigaChat-отчёта и нового CRM writable поля. Точное имя для будущего обновления берётся **из реального `crm.item.fields useOriginalUfNames=N`**, а не из самодельного преобразования.
- Только по новой отдельной авторизации оператора `-InspectLive -ApplyReconciliation -ApproveOneReconciliation` выполняется один POST `crm.item.update` c `useOriginalUfNames=N` и единственным полем, которое должно хранить `🟢 90/100 — высокий приоритет проверки`.
- Всё остальное (старый Score/version, GigaChat 9 полей, стадии, заголовок, контакты, задачи, клиенты) за пределами write allowlist; они должны совпасть в readback. До записи дважды проверяются карточка и значение, сохраняется бэкап и отдельный новый ключ `badge:1062:21:3:reconciliation-v1` **в том же** старом SQLite. Старый `UNCERTAIN` остаётся неизменным, не перезапускается и не очищается.
- После POST две проверки `crm.item.get` (Y/N) должны содержать ожидаемое значение. При любой неопределённости новая reservation остаётся UNCERTAIN; **повторять нельзя**, даже если поле пустое.
- Эта операция не меняет отображение поля на плитке канбана. `kanban_display_configured=false`. Выбор полей канбана — отдельный этап браузерной UI-приёмки, и его следует провести только после подтверждённой записи.

**Реально выполненная команда пока отсутствует; результат `BADGE_RECONCILIATION_VERIFIED` не заявляется до выполнения на компьютере владельца.**

Рекомендуемая последовательность:
```powershell
# 1. Отдельная подготовка; только GET
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $Script -PythonPath $Python -InspectLive
# 2. Только после прочтения результата READONLY_READY и отдельного решения:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $Script -PythonPath $Python -InspectLive -ApplyReconciliation -ApproveOneReconciliation
```

Это **восстановительная запись после анализа**, а не переисполнение исторической команды и не обход `UNCERTAIN`. Цель и объём строго ограничены тем же DEMO полем и карточкой, а новый факт согласия требуется потому, что предыдущая однократная попытка не была подтверждена.

Отдельно: Bitrix24 может игнорировать некорректный field key при `crm.item.update`, даже возвращая HTTP 200; это задокументировано в https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-update.html. Следовательно, новый write не гарантирует успешный readback и допускает только один запрос.


## Инцидент после операторской попытки PR #64 (02.11.2026)

После успешного `BADGE_RECONCILIATION_READONLY_READY` пользователь выполнил единственный `-InspectLive -ApplyReconciliation -ApproveOneReconciliation`, получил `BADGE_RECONCILIATION_BLOCKED_OR_UNCERTAIN` и остановился. Это сообщение подавляет фактическую стадию ошибки, поэтому нельзя утверждать, что запись в CRM была отправлена или успешно произошла.

Следующая **только read-only** проверка через `RUN_SERVICEIT_KANBAN_BADGE_READONLY_DIAG.ps1 -InspectLive` теперь показывает третий статус:
`ledger.items["badge:1062:21:3:reconciliation-v1"]` в дополнение к двум прежним. 

- `NOT_RESERVED`: новая резервирующая операция не была записана в журнал, следовательно запрос нового `crm.item.update` не был отправлен через `apply_reconciliation`. Одна из предпроверок или сохранение бэкапа могли остановить запуск.
- `UNCERTAIN`: запись была зарезервирована; невозможно определить, дошёл ли запрос и выполнился ли он. Проверить `readback_with_original_names` и `readback_with_camelcase_names` без повтора.
- `VERIFIED`: оператор смог подтвердить значение и закрыть журнал; всё равно сверить реальное значение, поскольку другие изменения могли произойти позже.

Сама диагностика не меняет никаких журналов и CRM. Не сбрасывать `UNCERTAIN`, не подбирать новые режимы записи, не использовать новый StateDir и не запускать старые команды с флагами изменения. Перед дальнейшими действиями нужен этот результат.
