# «Сервис ИТ»: БЕСПЛАТНАЯ облачная автоматизация новых карточек (GitHub Actions)

Дата: 02.11.2026. **Кандидат к запуску; по умолчанию выключен.**
Только Bitrix24 смарт-процесс `1062/21` и новые ID >=8. Не изменяет
источники лидов, финансовые процессы, VALYQON, исторические #3/#7, канбан.

## Почему бесплатно

Репозиторий `Ramzes2023/Service-IT-LeadGen` — **public**.
GitHub подтверждает бесплатные *стандартные* GitHub-hosted runner в
public-репозиториях. Cron минимально раз в пять минут, но график не является
гарантированным SLA: запуски могут задерживаться/пропускаться. Приватный
репозиторий ограничен включёнными минутами (GitHub Free 2000/мес.).
Платный Render или VPS не нужны. Нет непрерывного процесса 24/7: каждый
запуск кратковременный, но не зависит от включения ноутбука.

## Как сохраняется история без платной БД

GitHub Actions каждый раз стартует на новой виртуальной машине. Простая
SQLite без постоянного хранилища могла бы вызвать повторный AI-запрос и
повторную CRM-запись, что неприемлемо.

Поэтому создана отдельная ветка `serviceit-ai-encrypted-ledger` с файлом
`.serviceit/encrypted-ledger.txt`. Перед первым запуском в ней находится
строго заданная метка инициализации. После запуска:
- рабочая SQLite зашифрована `Fernet` (AES+HMAC) отдельным ключом,
  хранящимся только в GitHub Actions Secrets;
- запись `model_state=RESERVED` сохраняется в GitHub **до** API-вызова
  GigaChat, запись `write_state=RESERVED` — **до** `crm.item.update`;
- GitHub Contents API требует ожидаемый `sha` и подтверждает новый
  коммит. Не подтвердили резервирование — не выполняем внешний вызов;
- после каждой успешной серии сохраняется cursor, финальный статус, ID,
  а данные менеджера и ключи не публикуются;
- повреждённый/отсутствующий зашифрованный журнал или неправильный ключ
  **блокируют** работу, а не создают пустую базу и не начинают сначала;
- при неизменной SQLite пустые опросы не создают тысячи лишних коммитов.

**Важно:** ветка состояния в публичном репозитории видна всем, но её
содержимое шифруется. Не использовать её для текстовых данных клиентов,
возможные метаданные (размер/частота обновлений) публичны.
Защита зависит от сохранности секретного Fernet-ключа.

## Инструкция настройки (НЕ вводить секреты в чат)

1. Убедиться, что будущая автоматизация не пересечётся с локальной задачей
   Windows `ServiceIT-AI-Autofill-1062-21`. Перед включением GitHub-режима
   **выключить** локальную задачу, не удаляя DPAPI-секреты/старый журнал:

   `Disable-ScheduledTask -TaskName 'ServiceIT-AI-Autofill-1062-21'`

2. Проверить только чтением, какой **наибольший ID уже существует**
   в категории `21` процесса `1062`; установить в
   `SERVICEIT_GH_START_AFTER_ID` именно последнее ID до переключения.
   Значение >=7. Старые карточки должны быть отложены; работа начнётся
   со следующего ID. При изменении cutover после инициализации — стоп.

3. В GitHub `Settings > Secrets and variables > Actions` добавить
   **Repository secrets** (НЕ размещать в коде/PR):
   - `SERVICEIT_BITRIX_WEBHOOK`: разрешённый REST webhook именно
     `serviseit.bitrix24.ru` (только нужные CRM права);
   - `SERVICEIT_GH_LEDGER_KEY`: сгенерированный Fernet-ключ. Команда
     в локальном Python с cryptography: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
     Сохранить резервную копию в менеджере паролей. Потеря ключа = блокировка.
   - `GIGACHAT_CREDENTIALS`: Authorization Key GigaChat, разрешённый
     для корпоративных данных. Не использовать сам `Client ID`.

4. В той же странице добавить **Repository variables**:
   - `SERVICEIT_GH_START_AFTER_ID`: точный проверенный cutover ID;
   - `GIGACHAT_SCOPE`: точный `GIGACHAT_API_PERS` / `..._B2B` /
     `..._CORP`;
   - `SERVICEIT_WORKER_MODEL_PRIVACY_APPROVED`: `YES` **только**
     при корпоративном разрешении на передачу проверенных сигналов GigaChat,
     иначе `NO`.

5. Только после отключения Windows и настройки секретов поставить
   **Repository variable** `SERVICEIT_FREE_CLOUD_ENABLED=YES`.
   Это включит job по расписанию (или запуск через `Run workflow`).
   До этого job будет **skipped** и не затронет Битрикс.

6. Проверить в `Actions > ServiceIT Free Cloud AI Cards`: статус,
   без секретов; подтверждение существования зашифрованной ветки и
   правильный курсор. Если появляется `FREE_CLOUD_BLOCKED_REVIEW_REQUIRED`
   — не пытаться сбрасывать зашифрованную ветку; потребуется изучение журнала.

## ВАЖНО: что эта миграция пока НЕ решает

- Сам GitHub Actions — облачный **планировщик**, не независимый источник
  фактов о компании. При отсутствии девяти подтверждений новый лид получает
  честный `HOLD` (ждёт проверки), а GigaChat **не вызывается** и Score
  **не рассчитывается**.
- Нынешний worker пока не переводит уже записанный HOLD автоматически в
  VERIFIED после независимой проверки: требуется двухфазная логика
  дальнейшего обогащения с отдельным write-fence, тестами и readback.
- Сервис не инициирует исходящие звонки/сообщения и не создаёт вымышленные
  факты/контакты.
- Реальный облачный запуск и E2E с **новым разрешённым** CRM ID ещё
  не проверены. Миграцию нельзя называть готовым боевым AI-скорингом,
  пока все эти подтверждения не получены.

## Безопасность

Содержимое `GITHUB_TOKEN`, ключи GigaChat, Fernet и Bitrix в GitHub
Actions Secrets, НЕ в исходниках; не копировать их сюда. Workflow
выполняется только из main исходного public repo, при явном
`SERVICEIT_FREE_CLOUD_ENABLED=YES`. Запуск сериализован `concurrency`;
на ambiguous model/CRM call повторная операция не выполняется автоматически.
Рекомендуется периодически проверять GitHub Actions, потому что расписание
может задерживаться, а в неактивном public repo автоотключаться.
