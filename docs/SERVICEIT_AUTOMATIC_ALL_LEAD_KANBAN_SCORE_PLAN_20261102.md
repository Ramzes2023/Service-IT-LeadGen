# ServiceIT: автоматический цветной Score для каждого входящего сигнала

**Цель владельца (02.11.2026):** чтобы после скоринговой обработки *каждого* нового сигнала в канбане «Сервис ИТ — AI-сигналы» автоматически отображалась цветная оценка без ручного ввода. Не только для DEMO #3.

## Что уже работает и что не работает

- Есть исходный `assess_lead` (чистая функция анализа нескольких B2B-сигналов компании): рассчитывает **детерминированный** Lead Score, версию и факторы. GigaChat делает отдельные гипотезы и *не* задаёт число Score.
- На корпоративном Bitrix24 в изолированном смарт-процессе `entityTypeId=1062`, `categoryId=21`, у DEMO #3 уже отображается **90** на канбане.
- Дополнительное строковое пользовательское поле `UF_CRM_13_SVCIT_AI_SCORE_BADGE` («AI — цветной приоритет») создано в схеме `CRM_13`, доступно, но после нескольких попыток REST `crm.item.update` и ручного ввода в интерфейсе реальная проверка показала `EMPTY`. Два исходных write-ledger `UNCERTAIN` остаются нетронутыми. Значение и оформление цветной метки **не доказаны** в live CRM. Не повторять старые `-ApplyDemo`/`-ApplyReconciliation`.
- Поле Score 90 и полный GigaChat-отчёт не затронуты, реальных массовых источников/worker+CRM-адаптера пока нет.

## Новый слой автоматического форматирования

В `leadpilot/serviceit_kanban_presentation.py` встроен чистый, универсальный форматтер:
`score_label(n)` — 🟢 80–100, 🟡 60–79, 🔴 0–59. Это сохраняет визуальные границы первого теста. Красный здесь обозначает **приоритет проверки**, не полный отказ, а зелёный **не разрешает** маркетинговый контакт. Более тонкие пороги менеджерской бизнес-логики остаются вне цветной метки.

`assess_lead` автоматически добавляет `kanban_score_badge` в **каждый** ответ, независимо от источника, наличия GigaChat или того, находится ли компания в HOLD. В `plan_serviceit_ai_signals` теперь включены цветная метка, код целевого поля и `score_badge_write_performed=false`. Это нужно будущему корпоративному writer, чтобы передавать готовую метку вместе с числом и версией при **одном** разрешённом upsert, а не делать отдельную запись декоративного поля после создания карточки.

`fields_from_assessment` даёт три кода в формате структуры CRM (score, version и badge), **не вызывает** CRM и не даёт разрешения на запись. Оно проверяет, что оценка в допустимом диапазоне, версия присутствует, решение менеджера нужно, контакт через модуль не разрешён. Доставка в CRM должна быть разрешена и ограждена отдельно.

## Чтобы это работало НА ПОРТАЛЕ автоматически для всех

Отдельно необходимо:

1. Одобрить ограниченный реальный источник и настоящий корпоративный contract для записи с проверкой ФНС/ИНН, source evidence, глобальных CRM-дублей, клиентов, запретов и прав. Устранить HOLD и согласовать правила для безопасного сохранения *непроверенных* сигналов, если таких источников планируется показывать менеджерам.
2. Разработать и протестировать **инкрементальный** интеграционный адаптер с one-shot/идемпотентностью, который получает `assess_lead`, создаёт/обновляет каждый разрешённый элемент 1062 **одним полным запросом**, в том числе использует `fields_from_assessment` для формирования цвета. На ошибки — readback и reconciliation вместо слепого повтора.
3. Установить отображение заполненного пользовательского поля «AI — цветной приоритет» в *общих* настройках предварительного просмотра канбана, подтвердить под аккаунтом Микаила.
4. Проверить независимую E2E приёмку на нескольких новых синтетических карточках с разными оценками (например 🟢90, 🟡65, 🔴35), не меняя item #3 и не создавая исходящие сообщения/звонки. Только после этого можно говорить «автоматически видно на всех».
5. Для переоценки существующих элементов нужна отдельная синхронизация **по изменению версии/Score** с безопасным global dedup и журналом — никакой массовой записи без согласования.

### Чего данный PR НЕ делает

Никаких корпоративных CRM writes, вызовов GigaChat, подключения реальных источников, отправок писем/звонков, изменений воронок, общей канбан-конфигурации, запуска планировщика/рабочего сервиса и удаления/сброса прежних резервирований. Успех CI подтверждает лишь универсальное форматирование **в коде**, а не промышленную автоматизацию на портале.
