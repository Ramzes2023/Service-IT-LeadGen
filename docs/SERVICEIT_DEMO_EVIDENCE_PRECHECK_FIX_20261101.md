# Сервис ИТ — разбор первой блокировки AI LeadGen → Bitrix24 (01.11.2026)

## Подтверждённый реальный журнал

При исполнении объединённого PR #52 в корпоративном Bitrix24 на строго синтетической карточке `1062/21/#3` оператор вывел:

```text
GIGACHAT=LOCAL_KEY_FOUND_REDACTED
SERVICEIT_QUALIFICATION_BRIDGE=ONE_DEMO_1062_ITEM_3
BLOCKED_OR_UNCERTAIN; reason=DEMO_EVIDENCE_STATUS_MISMATCH
```

**Значение статуса доказательства в живой CRM не получено**. Нельзя утверждать, что оно пусто или соответствует конкретной иной строке. Причина: старый код требовал полного текстового равенства `UF_CRM_13_SVCIT_EVIDENCE_STATUS` с фразой `Синтетический тест — не реальная потребность`. В Bitrix поле может быть оставлено незаполненным или человек мог выбрать альтернативный непроверенный статус.

Важная граница: exception `DEMO_EVIDENCE_STATUS_MISMATCH` возник в `build_analysis()` **до локального резервирования SQLite и любого `crm.item.update`**. Этим запуском значения CRM не перезаписывались, задача №26163 не затрагивалась и новые задачи не создавались. Но прежний код выполнял вызов GigaChat **перед** проверкой этого статуса — поэтому факт использования локального ключа не доказывает запись AI-ответа в CRM.

## Исправление PR #53

- Оба *дополнительных* текстовых поля `...EVIDENCE_STATUS` и `...REVIEW_DECISION` допускают прежние канонические демо-метки, незаполненное/нулевое значение (маркируется `UNSET_UNVERIFIED`) или **только** заранее заданные однозначно непроверенные статусы (например `Ожидает проверки`, `Не проверено`, `DEMO`). Нормализация канонической метки затрагивает лишь регистр, пробелы и вид тире.
- Незнакомое **непустое** значение остаётся блокирующим: `DEMO_EVIDENCE_STATUS_NONEMPTY_REVIEW_REQUIRED` или `DEMO_REVIEW_DECISION_NONEMPTY_REVIEW_REQUIRED`. Это может быть вручную подтверждённое коммерческое решение, которое нельзя игнорировать. При ошибке выводится только безопасная форма значения: `POSSIBLE_ENUM_ID`, `HAS_SYNTHETIC_WORD`, `POSSIBLE_AFFIRMATIVE_STATUS`, `UNRECOGNIZED_TEXT` и др. **Исходное значение, имя, контакт, вебхук и содержимое CRM не выводятся.**
- Эти два поля **никогда не отправляются** в `crm.item.update` и не получают новых значений автоматически. Запись по-прежнему допускает **только 4 поля** *существующей* синтетической карточки №3: `LEAD_SCORE`, `SCORE_VERSION`, `MANAGER_NEXT_ACTION`, `STOP_REASON`.
- Сохранены: проверка 16 исходных UF, source/idempotency/фиктивного ИНН, категории 21 и действующей стадии, отсутствие реальных контактов, выключенная автоматизация, проверка версии score, `crm.item.fields` перед записью, локальная SQLite idempotency-резервация **до POST**, GET readback и вторичная проверка метаданных.
- Ключ GigaChat берётся только из ранее известной локальной конфигурации, без копирования его в GitHub или чат. Но теперь **сначала** проверяются идентичность карточки, срок сигнала, статусы и разрешённая схема UF, **после чего** выполняется AI-вызов на *фиксированной фиктивной фразе*. Гипотеза AI не изменяет числовой score и не разрешает контакты с реальными клиентами.

## Как проверять

После зелёного GitHub CI можно повторно запустить ограниченный `RUN_SERVICEIT_AI_LEAD_GENERAL_DEMO.ps1 -ApplyDemo -UseExistingGigaChat` **на новом закреплённом коммите**. Это повторение допустимо, потому что исходный блок был *до* попытки CRM POST. Если при повторе возникнет `BLOCKED_OR_UNCERTAIN`, **не запускать `-ApplyDemo` снова без проверки SQLite**: новый сбой может быть уже после POST.

Успех только при `SERVICEIT_DEMO_QUALIFICATION=DEMO_CRM_QUALIFICATION_VERIFIED`. Он подтверждает демонстрацию квалификации, score и AI-гипотезы **на синтетической карточке**. Работа с реальными лидами и корпоративными стоп-листами не запущена и не должна называться готовой.
