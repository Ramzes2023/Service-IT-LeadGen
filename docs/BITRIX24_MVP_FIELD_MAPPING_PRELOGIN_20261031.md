Основание: ТЗ Микаила v3.0, прежде всего §7, §8, §9 и требования к анализу контактов, ответственности, стоп-листу и фиксации этапов сделки. Этот паспорт — **не результат аудита корпоративного портала**. Приглашение на `serviseit.bitrix24.ru` получено, пользовательский вход и чтение метаданных API ещё не выполнялись.

## Границы создания и изменения

1. До подтверждённого интереса работаем с карточкой **Lead** в согласованной CRM-модели; после интереса — Company/Contact/Deal. **При этом** стандартные Лиды могут быть общими для портала, поэтому для теста нужен отдельный согласованный смарт-процесс/изолированный контур. Не считать сделочную воронку изоляцией Лидов.
2. Совпадение по **ИНН** означает ту же юридическую организацию, но **новый сигнал сохраняется отдельно**, историю не затираем. Совпадение телефона/email/домена между разными ИНН создаёт флаг ручной проверки, а не автослияние.
3. Повторная попытка отправки использует стабильную пару `organization_inn + signal_id`. Данные из локального симулятора, manager-review и AI не являются автоматическим разрешением.
4. Перед любым созданием CRM-элемента нужно пройти проверки: реальный сигнал, целевая организация, действующий клиент/дубли/стоп-лист, право коммуникации, решение менеджера, разрешение владельца портала. Роботы и маркетинговые действия выключены до отдельной приёмки.
5. CRM остаётся **системой учёта**, локальная SQLite — только upstream staging/review; отчёты по сделкам и оплатам не сочинять и не выводить из сгенерированных синтетических событий.

## Чек-лист первого входа, когда пользователь будет готов

- [ ] Участник входит через **своё** приглашение, проверяет, что адрес портала — `serviseit.bitrix24.ru`, и запрашивает подтверждение своей роли у администратора.
- [ ] Администратор указывает изолированный тестовый объект и подтверждает, что роботы/триггеры/авторассылки там выключены.
- [ ] Утверждаются реальные поля, стадии, права и ответственное лицо: только после этого можно заполнить столбец «Реальный код поля».
- [ ] С согласия руководства выдаётся **минимальный webhook только на чтение**. Хранить локально, не вставлять в чат или Git.
- [ ] Read-only preflight проверяет `crm.category.list`, `crm.item.fields`, безопасные методы проверки объекта, не выдавая клиентские списки в логи.
- [ ] Отдельно согласуются проверки действующих клиентов, дублей по ИНН и стоп-листов с минимальным доступом.
- [ ] **Только по отдельному разрешению** создаётся синтетическая тестовая запись, проверяется связь с задачей/сигналом, повтор без дубля и безопасный rollback. До этого `CRM_WRITES=NO`.

## Критерий передачи в реальный пилот

`CRM_ACCESS_APPROVED + TEST_OBJECT_ISOLATED + FIELDS_CONFIRMED + DUPLICATE_STOP_GATES_PASS + SYNTHETIC_WRITE_ACCEPTED + QUALIFIED_REAL_SOURCE_EVIDENCE + HUMAN_REVIEW`.

Ни один из этих операторских флагов **не подтверждён только фактом приглашения**. До согласованного теста: `CRM_READY=NO`, `OUTBOUND=NO`, `AUTHENTICATED_USERS=NOT_PROVEN`, `PRODUCTION_ACCEPTANCE=NO`.
