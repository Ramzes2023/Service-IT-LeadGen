# ServiceIT: смена стадии синтетической карточки №3 — защищённая проверка

## Факт из корпоративного read-only запуска

1 ноября 2026 года оператор PR #50 сообщил `EXACT_DEMO_GATE_EXACT_CARD_FAILED`. Из 14 полей совпали **13**. Единственный отказ — `stage_matches=false`. Все методы REST `crm.type.getByEntityTypeId`, `crm.enum.ownertype`, `tasks.task.getFields`, `crm.item.get` = OK; остальные gates = true; `task_created=false`, `crm_writes=NO`.

Это **не доказывает, на какую стадию была перемещена карточка**. До нового теста не следует менять стадию в UI или произвольно перезаписывать эталон `DT1062_21:CLIENT`.

## Как исправлено без изменения CRM

Стадия — изменяемое состояние работы со сделкой/смарт-процессом, тогда как ID, тип, категория, 16 UF, синтетический ИНН, источник, сигнал и отсутствие реальных контактов определяют идентичность карточки. Поэтому новая политика строго разделяет две вещи:

- Все остальные **13 immutable identity checks** по-прежнему обязательны без изменений.
- Если стадия точно `DT1062_21:CLIENT`, она проходит прежний gate (дополнительный REST не нужен).
- Если отличается **и все 13 идентифицирующих проверок прошли**, выполняется **один read-only** `crm.status.list` с точным фильтром `ENTITY_ID="DYNAMIC_1062_STAGE_21"`.
- Альтернативная стадия допускается **только** при строгом ASCII-формате `DT1062_21:<код>`, однозначном совпадении `STATUS_ID` со списком стадий категории 21, правильном `ENTITY_ID`, совместимом `CATEGORY_ID`, семантике `null`/пусто/`S` (никогда `F`), и отсутствии failure/apology в `EXTRA.SEMANTICS`.
- Если код не найден, стадия из другой категории, архивная/терминально провальная, API недоступен, список неоднозначен или содержит более 100 записей — **BLOCKED**. Никаких `crm.item.update`, переноса карточки и создания задачи при отказе.
- Роботы/бизнес-процессы остаются выключены, смарт-процесс 1062/категория 21/карточка #3 и те же original UF остаются проверяемыми.
- В ответе только статический `stage_policy=ORIGINAL_STAGE | REGISTERED_NON_FAILURE_STAGE | UNVERIFIED_STAGE_BLOCKED`, а также `alternate_stage_verified_in_category_21`. Новые имена стадий и данные корпоративных клиентов не логируются.

**Это осознанное уточнение прежнего слишком строгого правила:** переход по *официальной активной стадии той же изолированной DEMO-воронки* не должен делать учебную карточку другой сущностью. Все остальные safety checks не ослаблены.

При успешном read-only результате `NO_VISIBLE_MATCH_NOT_GLOBAL_PROOF` следующий этап — отдельная проверка наличия дублей и одноразовая внутренняя тестовая задача (может уведомить владельца корпоративного вебхука). Если `BLOCKED`, не повторять task POST.
