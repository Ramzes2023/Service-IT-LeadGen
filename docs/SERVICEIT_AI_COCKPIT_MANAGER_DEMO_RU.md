Текущее состояние: **CODE_READY**. В этой разработке не было вызовов корпоративного Bitrix24 или GigaChat, создания полей, применения карточки или записи отчёта. Проверки выполнены на моках. LIVE_FIELD_CREATED, PERSONAL_LAYOUT_APPLIED и DEMO_AI_REPORT_VERIFIED ещё не получены на портале.

Демонстрация предназначена только для смарт-процесса 1062, направления 21, элемента 3 «DEMO ServiceIT AI — DEMO-ITREQ-001». Это вымышленная компания, а не квалифицированный реальный клиент. Внутренняя задача 26163 сохраняется; оператор не вызывает методы задач. Старый VERIFIED ledger синхронизации оценки не открывается и не изменяется.

## Что увидит менеджер после отдельного применения

В начале личной карточки появится раздел «Сервис ИТ | AI-анализ». Порядок: Lead Score, версия оценки, статус AI, краткий вывод, дословная цитата, гипотеза потребности, ограничения, рекомендуемая услуга, действие, памятка менеджеру и «GigaChat — полный AI-отчёт». В полном отчёте есть объяснение факторов оценки, источник, ограничения, чек-лист, провайдер, модель и время UTC. Confidence модели не подменяет Lead Score.

Это стандартные поля и разделы CRM, без HTML, CSS, цветовых шкал или собственного виджета. Строковые поля создаются с настройкой ROWS от 2 до 18; полный отчёт — 18 строк и максимум 12000 символов. Фактическую высоту в режиме просмотра и поведение сворачивания определяет интерфейс Bitrix24; это нужно проверить вручную. В режиме редактирования доступно многострочное поле. Если веб-интерфейс показывает краткое превью, открыть редактирование поля/карточки — штатная альтернатива панели. Существующие разделы, включая неизвестные и интеграцию задач, сохраняются. Только перечисленные AI-поля и score/version могут переместиться в новый раздел; все их дополнительные настройки сохраняются.

Личная конфигурация `scope=P` принадлежит владельцу вебхука. Она **не становится автоматически видна Михаилу**. Проверять интерфейс нужно под тем же пользователем. Запись в общую конфигурацию `C` и чужой `userId` в операторе отключены. Если личная `P` равна `null`, оператор может **только прочитать** сохранённую общую `C` и подготовить её полную копию для собственной `P`. Для Михаила нужен его собственный авторизованный запуск личной настройки либо отдельная будущая административная процедура с проверкой полномочий, отдельным согласием и резервной копией. Автоматического перехода между C и P нет.

## Безопасная последовательность для локального оператора

Следующие команды предназначены для будущего отдельного запуска человеком на Windows. В рамках Codex их live-режимы не выполнялись. Запускать из корня этого worktree с уже одобренным Python в `SERVICEIT_PYTHON_FOR_TESTS`. Пакеты не устанавливать. Не вставлять вебхук или ключ в команду, чат, Git или снимок экрана.

1. Проверить локальную готовность, без сети и секретов:

   ```powershell
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1
   ```

2. Отдельно разрешённая read-only проверка схемы, личной карточки и DEMO-элемента; GigaChat не вызывается:

   ```powershell
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -InspectLive
   ```

   PowerShell запросит вебхук через `Read-Host -AsSecureString` (уже проверенный в прежнем Bitrix-операторе). Набираемый/вставленный URL не отображается. Он передаётся в Python только через временную переменную окружения дочернего процесса и удаляется после вызова; Python `getpass` не используется. Вебхук должен относиться к `serviseit.bitrix24.ru`. Нужны права чтения CRM, `crm` и `userfieldconfig`. По официальному контракту Bitrix24 личная конфигурация `P` может легально быть `null`: это означает отсутствие сохранённой личной настройки. Read-only preview теперь различает три ситуации: `PERSONAL_SAVED` (P сохранена), `INHERITED_COMMON` (P=null, C — полный сохранённый список), `UNSAVED_DEFAULT` (P=null, C=null). При `INHERITED_COMMON` общая C только читается; первоначальный личный layout отсутствует, поэтому будущий SET разрешён **только в P**, с полной копией всех элементов C и добавленным AI-разделом, проверкой неизменности P/C, бэкапом обеих исходных настроек и GET после SET. После создания личной P изменения общего оформления C могут больше не наследоваться этим пользователем — это особенность отдельной настройки.
При `UNSAVED_DEFAULT` можно завершить read-only preview, но применение layout **блокируется** с `LAYOUT_DEFAULT_REQUIRES_MANUAL_BASELINE`: REST не отдаёт полный встроенный layout, и мы не создаём опасную частичную замену. В этом случае сперва нужно сохранить личную настройку из штатного редактора Битрикс24 и затем повторить предпросмотр. Ответы `[]`, `{}` и неполные объекты не приравниваются к `null`. Неоднозначная схема, пагинация или несовпадение typeId=13 по-прежнему блокируют запись.

3. Предпросмотр новых полей, затем отдельное создание:

   ```powershell
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode provision -InspectLive
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode provision -InspectLive -ApplyDemo
   ```

   Нужны права «Разрешить изменять настройки». Используются только `userfieldconfig.list/get/getTypes/add`; `entityId=CRM_13`, тип `string`, имена до 50 символов. Существующие совпадающие поля переиспользуются, несовместимые типы, краткие ROWS и дубли блокируют работу. Исходные 16 полей обязательны и не изменяются. Метаданные типа должны явно подтверждать отключённые роботы и бизнес-процессы; оператор их не отключает сам. Проверяются исходные synthetic kind и idempotency key элемента. Новые поля принадлежат схеме всего процесса 1062, а не исключительно элементу 3; значения записываются только в 3, конфигурация ограничена направлением 21.

4. Предпросмотр и применение только личной конфигурации:

   ```powershell
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode layout -InspectLive
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode layout -InspectLive -ApplyDemo
   ```

   Перед SET сохраняется полный исходный JSON и предлагаемый результат; при P=null также сохраняется унаследованный снимок C, если он существует. Затем повторный GET должен точно совпасть с исходным; SET передаёт весь массив разделов, GET после SET должен точно совпасть с предложением. При нормализации неизвестных опций сервером результат считается неопределённым и требует ручной проверки, а не повторного SET.

5. Предпросмотр отчёта без AI, затем отдельное заполнение со свежим GigaChat:

   ```powershell
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode populate -InspectLive
   .\scripts\RUN_SERVICEIT_AI_COCKPIT_DEMO.ps1 -Mode populate -InspectLive -ApplyDemo -GigaChatOptIn -SyntheticPrivacyOptIn -UseExistingGigaChat
   ```

   Для второго запуска `-UseExistingGigaChat` (добавлен после успешного реального preflight 01.11.2026 с `quality=complete`) берёт локальные GigaChat-настройки из того же строго ограниченного списка пяти одобренных путей, что и отдельный проверенный оператор PR #59. Эта опция допустима **только** вместе с `-Mode populate -InspectLive -ApplyDemo -GigaChatOptIn -SyntheticPrivacyOptIn`; без флага существующие переменные окружения продолжают использоваться как прежде. Оператор не читает файлы вебхуков/cookie, не публикует ключи и восстанавливает GigaChat-переменные окружения в `finally`. До резервирования однократной операции `populate` проверяет локальную конфигурацию GigaChat; отсутствие ключа/выключенная модель не расходуют reservation. При таймауте или недопустимом ответе *после* резервирования повторные POST/модельный вызов по-прежнему запрещены. TLS-проверка включена. Модели отправляется только фиксированная учебная фраза из существующего модуля, никогда данные карточки. Только `quality_status=complete`, положительная конечная confidence, разрешённая услуга и дословная цитата допускаются к отчёту. Свободный текст модели проверяется на опасные конструкции и не копируется как установленный факт: карточка получает ограниченную гипотезу применимости услуги. Полный отчёт не сокращается до короткой строки.

Основной оператор — PowerShell-скрипт выше с `-PythonPath` (при необходимости). Прямой вызов Python для live-запросов теперь требует явный `--webhook-from-env` и заранее безопасно подготовленное `SERVICEIT_AI_COCKPIT_WEBHOOK`; без этого вызов прекращается с фиксированным кодом, **никакого Python getpass**. Поэтому используйте только PowerShell-оператор. Без `-InspectLive` возможен полностью офлайн preview. В данном PR никаких live-команд не выполнялось.

## Журнал, резервные копии и неопределённый результат

По умолчанию PowerShell использует `%LOCALAPPDATA%\ServiceIT\AI-Cockpit-Demo-v1`. Новый файл `cockpit-report-v1.sqlite3` содержит отдельную таблицу cockpit_ops. Резервные JSON сохраняются с уникальными именами до каждого изменения. Хранить каталог локально с правами оператора: схема и конфигурация могут содержать внутренние названия. Секретов в этих файлах нет. Не коммитить каталог состояния.

Резервирование атомарное (`BEGIN IMMEDIATE`, UNIQUE key, synchronous FULL). Ключи фиксированы для каждого поля, личной конфигурации и единственного отчёта 1062/21/3/v1. Резерв создаётся **до** POST, для отчёта — ещё до запроса AI. При timeout, ошибке авторизации, несоответствии readback или падении процесса остаётся UNCERTAIN. Повторный POST заблокирован. Нельзя удалять журнал, менять каталог состояния или придумывать новый ключ ради повторения. Успешно созданные поля и уже совпадающая конфигурация распознаются по свежему GET без повторной записи. Для отчёта повторный запуск блокируется даже после VERIFIED: это одна демонстрация, не периодический production refresh.

При UNCERTAIN администратор должен отдельно получить read-only состояние CRM, сопоставить с резервной копией/предложением и журналом, зафиксировать фактический результат. Автоматического восстановления, сброса резерва или отката нет. Это сознательное ограничение до корпоративной приёмки: повторение записи или откат могут затереть параллельную работу. GigaChat completion в новом режиме также не повторяется даже при 401; существующие вызовы AI сохраняют прежнее поведение.

Предыдущая проверка (до данного исправления): 69 тестов cockpit; полный офлайн-набор — 861 passed, 26 subtests passed. Цитата модели проверяется целиком до любого сокращения; неподтверждённая цитата блокирует отчёт. Любое уже заполненное новое AI-поле блокирует повторную запись ещё до вызова модели, даже с новым каталогом состояния. Не менять каталог для обхода UNCERTAIN: отсутствие отчёта в CRM не доказывает, что предыдущий запрос не был выполнен. Моки не подтверждают полноту унаследованной личной конфигурации на реальном портале; это остаётся условием отдельной приёмки.

Открыть корпоративный портал под владельцем вебхука → CRM → нужный смарт-процесс → направление 21 → найти именно DEMO-ITREQ-001 → элемент 3. Проверить отсутствие реальной компании/контактов, сохранность старых разделов и задачи 26163, порядок полей и читаемость полного отчёта. Сверить цитату с учебной фразой из `AI_TEXT`; это проверка текста синтетического fixture, а не подтверждение клиентского спроса и не извлечение из реальной публикации. Проверить score/version, стоп-причину и исходные 16 полей: новый оператор их не обновляет. Сигнал должен оставаться учебным и требующим проверки. Не звонить и не писать клиентам.

Проверить, что значения новых полей точно совпали с GET после update, а layout — с GET после SET. Серверные привилегии и фактическое отображение ROWS нельзя доказать моками. Если портал возвращает другую форму JSON, отказывает в scopes, нормализует конфигурацию или меняет типы, остановиться: адаптер должен остаться read-only до отдельного исправления и приёмки. Production-адаптер отсутствует; реальные сигналы требуют независимых проверок компании, клиента, дублей во всей CRM, стоп-листов, источника и правового основания.
