# Инцидент Trudvsem pagination: offset=50 вместо offset=1

Дата: 31 октября 2026 года. Статус: **исправление отправлено в черновой PR #14, повторный реальный запуск ожидается**.

## Фактические наблюдения из Windows

1. Перед попыткой `pytest` дал **136 passed (4,23 s)**: локальный тестовый набор был неполон, поскольку допускал ошибочное понимание параметра `offset`.
2. Команда `source-scan --region 77 --term 1С --limit 50 --offset 50` вернула `SOURCE_STATUS=UNAVAILABLE; NO_REAL_RECORDS_CLAIMED; ValueError`. Реальный ответ API в отчёте не сохранён, точное содержимое ValueError неизвестно.
3. Файл `exports/round2_offset50/trudvsem_77.json` не создан. Регион 50 не был запрошен (цикл прерван).
4. При отдельном запуске `multi_page_precheck` закономерно получена ошибка `Missing saved source for region 77, offset 50`.
5. После обеих ошибок пользователь вручную запустил строку `Write-Host MULTIPAGE_FNS_BATCH=READY`. Это **ложное сообщение**, не доказательство готового списка. `exports/round2_combined_inns.txt` не появился.

## Причина и независимая проверка

В документации API «Работа России» параметры `limit` и `offset` относятся к пагинации: https://trudvsem.ru/opendata/api . В стороннем техническом разборе API `offset` описан как **номер страницы с нуля**, не количество пропущенных строк: https://habr.com/ru/articles/1052894/ . Независимые тесты внешнего коллектора подтверждают то же: https://github.com/alekseevpavel04/ru-it-jobs-radar/blob/main/docs/sources.md .

Следовательно, для страницы 2 при `limit=50` нужно использовать **`offset=1`**. Старый `offset=50` обращался к странице 51, и отсутствие ожидаемой структуры/ответа нельзя принимать за отсутствие вакансий. **Последний конкретный ValueError не был расшифрован в старом CLI, поэтому его детальный первоисточник неизвестен**.

## Исправления

- `leadpilot.sources.scan`: ограниченные номера страниц `offset=0..4` вместо 0..200, но прежний `limit<=50`; запросы только на фиксированный официальный `https://opendata.trudvsem.ru/api/v1/vacancies/region/<код>`.
- `leadpilot.multi_page_precheck`: принимает страницы `0,1,2,3,4`, а не `0,50,100,...`; строго проверяет метаданные входных снимков.
- `leadpilot.sources.scan` + `leadpilot.cli`: различают не-JSON HTTP 200 и неожиданную структуру через безопасные коды ошибок (`API_NON_JSON_RESPONSE`, `API_SCHEMA_MISMATCH`) без публикации тела ответа.
- Тесты теперь доказывают применение `offset=1`, отклоняют 50 как недопустимый индекс, проверяют обработку не-JSON и отсутствующих полей. Базовые 136 + 4 новых случая = **ожидается 140 тестов**, число не считается подтверждённым до нового запуска.
- `scripts/RUN_1C_PAGE1_RECOVERY.ps1` — один операторский скрипт с проверками каждого шага. При сбое печатает `MULTIPAGE_FNS_BATCH=FAILED` и возвращает код 1. `READY` печатается **только после создания и копирования настоящего TXT**; если новых ИНН нет, отдельный статус `NO_NEW_INNS`.

## Безопасное восстановление

Старые файлы первой страницы: `exports/round2_offset0/trudvsem_77.json`, `exports/round2_offset0/trudvsem_50.json` — **сохранить**. Не переименовывать папку `round2_offset50` в `offset1` и не фабриковать отсутствующие региональные ответы.

На правильной ветке PR #14 сначала выполнить `git pull --ff-only`, потом:

    powershell -NoProfile -ExecutionPolicy Bypass -File scripts/RUN_1C_PAGE1_RECOVERY.ps1

Скрипт пройдёт тесты, сохранит новые файлы **в отдельной папке** `exports/round2_offset1` и объединит список новых ИНН по страницам 0 и 1. Выполнение read-only по внешнему API, без записи в Битрикс24 и без коммерческих контактов.

## Что не доказано

Новый `offset=1` ещё не проверен на реальном API с Windows. Новые вакансии и ИНН могут появиться, а могут отсутствовать; нельзя обещать число клиентов. Корпоративный Битрикс24 и VALYQON не затрагивались.
