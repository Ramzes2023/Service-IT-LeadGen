# Service IT: массовая AI-обработка новых карточек, 04.11.2026

## Фактическая проблема

Резервный GitHub Actions poller до этого отправлял **не более 1** подписанного события нового объекта за запуск. Срабатывания GitHub schedule фактически были реже заявленных десяти минут (например, 04.11 в 14:45 UTC — один успешный опрос с 0 новыми карточками). При ожидаемых ~300 карточках/месяц потребовался независимый многоэлементный catch-up, который **не создаёт тестовые записи** и не запускает циклы по старым клиентам.

## Новый отдельный контур

`.github/workflows/serviceit-bitrix-all-new-batch-ai.yml` — плановый запуск (cron best effort), только `main`, только при уже разрешённых двух переменных `SERVICEIT_BITRIX_POLL_ENABLED=YES_1062_21_READONLY` и `SERVICEIT_BITRIX_EVENT_AI_ENABLED=YES_1062_21_CLOUD`.

`leadpilot/serviceit_bitrix_batch_worker.py`:
1. Строго проверяет GitHub run, портал, права/конфигурацию GigaChat и время owner cutover.
2. Сначала положительно калибрует `crm.item.list` на неизменяемой исторической контрольной карточке #3, **не записывая её**. Не доверяет ответу `[[]]` или неоднозначной пагинации.
3. Ищет все новые ID только `entityTypeId=1062/categoryId=21` после cutover (окно до семи дней, максимум 200 ID, все страницы проверены).
4. Для каждого ID смотрит существующий **зашифрованный** GitHub receipt. Уже резервированные карточки не переобрабатывает.
5. До **шести** ещё не зарезервированных карточек последовательно передаёт тому же `serviceit_bitrix_dispatch_worker.run()`, что обрабатывает настоящее подписанное событие. Внутренний подписанный ID-only envelope создаётся лишь после полностью проверенного списка на доверенном scheduled Actions runner. Этот процесс не подменяет вебхук и не предоставляет внешнюю точку приёма.
6. Стандартный обработчик делает `crm.item.get`, анализ всех девяти полей по действующим правилам и опциональный реальный GigaChat только при отдельных корпоративных privacy/evidence gates, бронирует CRM write в одноразовом ledger, выполняет защищённый `crm.item.update` и точный readback.
7. При неопределённой записи возвращает `BATCH_REVIEW_REQUIRED` и прекращает пакет. Никаких слепых повторов. Дальнейшие записи не выполняются после неясного результата.
8. Логи содержат только общее количество кандидатов, обработанных, HOLD/неопределённых и записей. Имена, INN, ID, секреты, email не выводятся.

Работает параллельно с прежним резервным event poller; оба используют один и тот же encrypted receipt и общую GitHub Actions concurrency группу, так что двойного CRM update одного ID быть не должно. Stage3 задачи и Stage4 формальный Score остаются отдельными разрешёнными процессами, не включаются этим обновлением.

## Проверки и границы заявления LIVE

- CI: новые offline tests проверяют несколько новых карточек в одном запуске, отсев дублей, лимит, режим HOLD/ошибку, точность HMAC и запреты до сети.
- GitHub cron — best effort. Это **не** гарантия обработки 300 карточек/месяц или 24/7 SLA при зависании/потере scheduled runs, GitHub quota, недоступности Bitrix24.
- Если модель не имеет согласия на передачу данных, все девять AI полей содержат честную детерминированную предварительную аналитику HOLD, а не выдуманные результаты GigaChat.
- Итоговый Score от 0 до 100 остаётся запрещён, пока нет реальных **девяти корпоративных подтверждений**, включая ФНС/ИНН, корпоративную дедупликацию/STOP, legal/manager gates.
- **Источник B2B-Center → Gmail V9 не активируется** этим изменением. Чтобы новые закупки вообще появлялись, требуется проверенный Apps Script V9 и одноразовый Google OAuth consent. Входящие каналы кроме B2B не считаются подключёнными из факта наличия кода.
- Нет правок исторических карточек, стадии, клиентов, касаний или рабочей воронки поддержки; новый pipeline работает только по новым объектам в одобренной тестовой категории.
- После merge проверить успешный scheduled run и при появлении настоящих новых объектов наличие encrypted receipt + exact CRM readback девяти полей и задач. Пока нет такого факта — нельзя сообщать Микаилу о полностью завершённой сквозной интеграции.
