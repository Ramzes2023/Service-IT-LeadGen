# Отдельный STOP-лист сигналов «Сервис ИТ» — v1

Это **НЕ** корпоративный STOP-лист компании. Он создан с нуля, только для **новых** сигналов LeadGen в смарт-процессе **1062 / воронка 21**. Другие CRM-воронки, техподдержка, компании, контакты и исторические карточки не меняются.

## Где хранится список

`config/serviceit_own_signal_stop.json` — отдельный версионируемый файл в репозитории. На старте `"rules": []`: никаких запрещённых компаний мы не выдумываем. Если список пуст, автообработчик возвращает `OWN_SIGNAL_STOP_ACTIVE_EMPTY`, **не** выдаёт решение «проверен весь корпоративный STOP» и **ничего не пишет** в CRM.

Для добавления **своей** отклонённой компании владелец проекта меняет файл через отдельный Pull Request (проверка и журнал GitHub). Формат:

```json
{
  "version": "serviceit-own-signal-stop-v1",
  "scope": "serviseit.bitrix24.ru:1062/21",
  "rules": [
    {"kind": "inn", "value": "ИНН_ИЗ_РЕАЛЬНОЙ_КАРТОЧКИ", "reason": "NOT_RELEVANT"}
  ]
}
```

Пример значения выше — **заглушка**, её нельзя оставлять в боевой конфигурации. Указывать только действительно проверенный ИНН реального сигнала и осознанную причину решения. Допустимые причины:

- `REJECTED_BY_SERVICEIT`: проект отказался от сигнала;
- `NOT_RELEVANT`: не соответствует услугам;
- `INVALID_SIGNAL`: ошибочный/ложный сигнал;
- `ALREADY_REVIEWED`: уже вручную обработано;
- `DO_NOT_REPROCESS`: не повторять автоматическую обработку.

**Правило v1:** только точное совпадение ИНН (10/12 цифр с контрольной суммой). Записи с таким ИНН будут HOLD для *всех будущих сигналов* этого ИНН; если надо блокировать только одну конкретную закупку, не добавлять ИНН в список без согласования — нужна следующая версия с точным идентификатором сигнала. Персональные данные, телефоны, email, вебхуки и секреты в файл не добавлять. Если в GitHub содержатся коммерчески чувствительные ИНН, доступ к конфигурации должен быть ограничен.

## Облачная автоматизация

- `serviceit-own-signal-stop-auto.yml`: каждые 20 минут и по подписанному событию появления новой карточки; явное разрешение именно на этот отдельный тип проверки встроено в workflow, корпоративный STOP-флаг не используется.
- `leadpilot/serviceit_own_signal_stop_auto.py`: ищет только новые 1062/21 после заданной даты запуска, читает только свой список и поле ИНН. Если правило совпало, добавляет **один внутренний комментарий** `[SERVICEIT_OWN_SIGNAL_STOP_V1] HOLD` с кодом причины. Повторные записи защищены отдельным зашифрованным одноразовым журналом; неопределённый результат записи никогда не повторяется вслепую.
- `serviceit-stage4-fns-dedup-readonly.yml`: существующий обработчик сигналов также проверяет собственный STOP и возвращает `HOLD_OWN_SIGNAL_STOP_MATCH`. Проверка происходит **до** корпоративной дедупликации/ФНС, не опирается на наличие корпоративного списка.
- Если ИНН не указан или некорректен — `HOLD_MISSING_VALID_INN`; отсутствие совпадения в нашем собственном списке **не является** разрешением продаж, окончательным Score, доказательством отсутствия существующего клиента или результатом корпоративного STOP.

## Ограничения доказанного состояния

Пока список пуст, **реальный HIT и комментарий в Bitrix24 не подтверждены**. Не использовать выдуманный ИНН/карточку ради демонстрации. После добавления первой настоящей записи сверить exact readback комментария новой настоящей карточки и статус GitHub Actions. Наша автоматизация **не блокирует системными правами Битрикс24** дальнейшие действия человека и не меняет стадию; она пишет внутреннюю HOLD-метку для команды. Для абсолютного запрета отправки лидов потребуется добавить этот собственный STOP в каждый отдельный downstream sender и проверить, что ни один обходной канал не отправляет сообщение.
