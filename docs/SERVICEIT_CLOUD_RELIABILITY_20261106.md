# Сервис ИТ — надёжность облачной автоматизации (06.11.2026)

## Результаты проверки реальных GitHub Actions

Учитывались только cron-запуски (event=schedule), а не плановые пропуски
на нерелевантных комментариях.

| Задание | Настроено | Самый большой наблюдаемый перерыв |
|---|---:|---:|
| Bitrix24 new-card polling fallback | 10 мин | 501 мин |
| AI all-new batch | 10 мин | 493 мин |
| Stage3 manager task | 10 мин | 473 мин |
| Preliminary Lead Score | 10 мин | 500 мин |

Зарегистрированные запуски могут приходить с задержкой или отсутствовать.
Сведения GitHub REST не позволяют уверенно отличить пропущенный cron
от доставленного с большим опозданием события. Гарантированный 10-минутный
SLA нельзя заявлять.

## Новая техническая защита

- Отдельный Python монитор leadpilot/serviceit_cloud_reliability_watchdog.py
  наблюдает семь критических процессов и НЕ читает CRM/телефоны/письма
  и не вызывает Bitrix REST.
- GitHub workflow serviceit-cloud-reliability-watchdog.yml запускается после
  завершения основных заданий (workflow_run.completed), по резервному cron
  в 23-ю и 53-ю минуты часа, а также вручную.
- Наблюдаемый журнал: GitHub Issue #221, назначен Ramzes2023.
- Контроль: разрывы между запусками, число зарегистрированных cron за 6 часов,
  ошибки и отмены, пропущенные/редкие исполнения, восстановление работы.
- Статусы: STALE, SPARSE, NO_SCHEDULE_RUN, SCHEDULE_FAILED, SCHEDULE_SKIPPED,
  WARMUP, RUNNING, OK.
- При изменении статуса одно сообщение в Issue и изменение его состояния;
  при одинаковом состоянии очередные комментарии не создаются.
- Гарантировать доставку push/email можно только при включённых
  уведомлениях GitHub для владельца, репозитория и назначенного Issue.
- Безопасные GitHub GET запросы могут повторяться при временных сетевых
  сбоях и 429/500/502/503/504; неоднозначные POST/PATCH не повторяются.
- Никаких автоматических повторных CRM item.update, tasks.task.add,
  crm.status.add. Каждый Bitrix writer использует отдельный журнал
  однократных операций, при UNVERIFIED/UNCERTAIN требуется точное чтение
  существующей записи, а не повторное создание.
- Планово выключенный формальный Score без корпоративных девяти
  подтверждений НЕ учитывается как авария.

## Приёмка после объединения кода

В GitHub Issue #221 комментарий только от Ramzes2023:
SERVICEIT_CLOUD_WATCHDOG_RUN_READONLY_V1

Проверить один успешный запуск ServiceIT Cloud Reliability Watchdog,
значение monitored_workflows=7, crm_writes=0, корректное обновление Issue,
отсутствие повторных сообщений при неизменном статусе.
Отдельно проверить получение уведомления в GitHub Notifications.

## Ограничение самого мониторинга

Он тоже работает на GitHub. При полном отсутствии GitHub Actions событий
монитор не гарантирует, что разбудит сам себя. Для строгого SLA и внешнего
обнаружения полного сбоя нужен независимый внешний heartbeat на другом
сервисе. GitHub Actions schedule остаётся best-effort.
