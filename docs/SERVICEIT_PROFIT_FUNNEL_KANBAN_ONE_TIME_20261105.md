# Сервис ИТ — интеграция прибыли, отдельной воронки и Канбана (05.11.2026)

## 1. Расчёт вознаграждения: РВП 15% / 10% / 75%

**Предложение владельца**, не утверждённая ещё работодателем система выплат:

- оплаченная выручка **без НДС** минус прямые подтверждённые расходы = расчётная валовая прибыль (РВП);
- разработчик системы: **15% от положительной РВП**;
- менеджер, действительно проведший продажу: **10% от положительной РВП**;
- компания: остаток (**75% при этих ставках**);
- если РВП отрицательная/нулевая, ни разработчику, ни менеджеру не начисляется бонус, отрицательный остаток остаётся компании.

Пример из задания: 5 000 ₽ *без НДС* − 1 000 ₽ расходов = **4 000 ₽**, разработчику **600 ₽**, менеджеру **400 ₽**, компании **3 000 ₽**. Если 5 000 ₽ — цена с НДС, перед расчётом требуется подтверждённая сумма без НДС, НЕ считать 5 000 ₽ чистой выручкой автоматически.

Модуль: `leadpilot/serviceit_profit_allocation.py`, функции `split_profit` (расчёт без разрешения выплаты) и `company_approved_split_draft` (строгое использование уже предусмотренного `calculate_approved_draft` с банковскими документами, корпоративными ролями, подтверждёнными расходами, подписанной схемой мотивации и привязкой конкретной сделки к новому сигналу). Доли задаются параметрами, не спрятаны в AI.

**Принимать 15/10/75 как ставку для зарплаты без утверждения руководства нельзя.** Финансовая роль подтверждает доходы и прямые расходы, компания утверждает расчётные периоды, дату запуска, отсечку участия и получателей. Отдельный контроль против повтора оплаты и журнала начислений обязателен. Авторассылка и перевод денег отсутствуют и не включены. В Битрикс24 нет утверждённой системы оплаты и доступа к банковским выпискам, поэтому автоматическую выплату не изображаем.

## 2. Создание отдельной воронки «Лидогенерация»

Официальный Bitrix API: `crm.category.add` для `entityTypeId=2` (сделки). Важно: это другая сущность, чем AI-сигналы `1062/21`; воронка **«Техническая поддержка» не меняется**. API требует CRM admin. `crm.category.list` скрывает воронки без прав, поэтому отсутствие названия у неадминистратора не является доказательством отсутствия.

- Модуль: `leadpilot/serviceit_sales_funnel_provision.py`.
- Облачный workflow: `.github/workflows/serviceit-sales-funnel-guarded-once.yml`.
- Owner-only безопасное чтение: комментарий `SERVICEIT_SALES_FUNNEL_READONLY_ONCE_V1` в GitHub Issue #148.
- Owner-only одноразовое создание (проверяет admin до POST): комментарий `SERVICEIT_SALES_FUNNEL_CREATE_ONCE_V1` в Issue #148.
- Прежде чем создать: реальный `user.admin=true`, полное доступное админу чтение categories, отсутствие совпадения по названию.
- Если уже существует: только `crm.category.get`, `crm.status.list`, без повторного создания.
- Если нет: одноразовое encrypted reservation в защищённой ветке `serviceit-ai-encrypted-ledger`, `crm.category.add` с точным `{entityTypeId:2,fields:{name:"Лидогенерация",sort:550}}`, строгий readback. Сомнительный POST → **никогда не повторять без отдельного расследования**. Не вызывать `crm.deal.add`, `crm.deal.update`, `crm.item.update`, `crm.category.update/delete`, чужие stage methods.
- Битрикс автоматически создаёт стадии по умолчанию для новой воронки. Для соответствия ТЗ v3.0 администратор **один раз** вручную настраивает их в собственной воронке (и проверяет, что не меняет иные): `Есть интерес` → `КП/расчёт` → `Переговоры` → `Согласование` → `Успешно реализовано` / `Закрыто без продажи`.
- Реальные сделки создавать только после проверки коммерческого интереса менеджером, существующего клиента и разрешённой CRM-связи «Сигнал потребности → Лид/Контакт/Компания → Сделка». Не превращать вакансии и HOLD в продажи.

Если `CRM_ADMIN_REQUIRED_NO_WRITE`: существующий webhook не способен создать воронку. Корпоративный администратор создаёт **новую** воронку в CRM → Сделки → Воронки или предоставляет временный **минимально необходимый** административный доступ для единичной операции; токены в чат/коммиты/Issue не отправлять. После этого owner-only workflow проверяет результат и не создаёт дубль.

## 3. Канбан: один раз включить у администратора, дальше автоматически

Уже действующие фоновые облачные обработчики автоматически заполняют 9 AI-полей в **каждой новой подходящей** карточке 1062/21 после обработки; `AI_SUMMARY` начинается со знака типа сигнала, затем статус и рекомендация. Отдельный предварительный `Lead Score` появляется только когда действующие допустимые условия выполнены; отсутствие независимой ФНС/STOP не считается проверенной продажей.

Добавлен машинный handoff: `leadpilot/serviceit_kanban_admin_handoff.py` → `one_time_admin_handoff()`. Администратор один раз открывает **Сервис ИТ — AI-сигналы → конкретная категория 21 → Канбан → Настроить карточку просмотра** и для **всех сотрудников** включает поля в порядке:

1. `title` — название;
2. `UF_CRM_13_SVCIT_AI_SUMMARY` — краткий вывод с 📑/👥/🎯 и статусом;
3. `UF_CRM_13_SVCIT_AI_STATUS` — AI-статус;
4. `UF_CRM_13_SVCIT_AI_SCORE_BADGE` — цветной предварительный/подтверждённый приоритет;
5. `UF_CRM_13_SVCIT_LEAD_SCORE` — числовой Score, когда допустим;
6. `UF_CRM_13_SVCIT_SUGGESTED_SERVICE` — предлагаемое направление.

Если места мало: **AI_SUMMARY + AI_SCORE_BADGE**. Сохранить общий вид, открыть от имени двух сотрудников и убедиться, что у них одинаковое отображение. Личные переопределения могут потребовать сброса.

Для полной карточки уже есть защищённый административный сценарий `.github/workflows/serviceit-manager-layout-safe.yml`: сначала предварительный просмотр, затем **одна** согласованная операция с encrypted backup и exact readback; текущий webhook не подтвердил административные права. Он не заменяет отдельную UI-настройку мини-плитки Канбана.

После однократного включения у администратора новые карточки автоматически пользуются этой формой и заполненными полями, **без ручного оформления каждой записи**. Это не доказывает live E2E до появления первой реальной новой карточки.

## 4. Что ограничивает полный production

- Корпоративный admin для создания/настройки новой воронки и общего вида, менеджер для проверки Kanban.
- Подтверждённые FNS/CRM/STOP/законность контакта и источник официального клиентского интереса — без них нельзя превращать HOLD в квалифицированную продажу.
- Факт новой реальной записи и доказательство цепочки AI/Score/task (последние live запуски возвращали ноль кандидатов).
- Менеджерское подтверждение звонка и реальная CRM-связь activity→deal. Письма и робозвонки не запускать без правового основания.
- Финансовые утверждения, учёт и документы на фактические поступления и расходы; без них нет автоматического реального начисления или выплат.

Исходное ТЗ v3.0 остаётся первичным договорным документом. Новые модули не внедряют живую зарплатную схему без согласования компании.


## 5. Временный администраторский вебхук (только однократное действие)

Никогда **не заменять** регулярный `SERVICEIT_BITRIX_WEBHOOK` на административный: он используется круглосуточными AI/задачами/Score. Для одной операции компания может разрешить отдельный `SERVICEIT_BITRIX_CRM_ADMIN_ONETIME_WEBHOOK`, сохранённый в GitHub Settings → Secrets and variables → Actions → Repository secrets. Доступ и срок действия согласовывает корпоративный администратор; токен не размещать в чате/Issue/PR/логе.

- Одноразовый workflow создания новой воронки `serviceit-sales-funnel-guarded-once.yml` предпочитает отдельный админский секрет, а при его отсутствии только безопасно проверяет прежний вебхук и блокирует запись, если нет прав.
- Применение общей формы Канбана через `serviceit-manager-layout-safe.yml` использует временный секрет **только для apply**, а предварительное чтение оставляет обычный вебхук. Нужны явные флаги `SERVICEIT_MANAGER_LAYOUT_ADMIN_APPROVED=YES` и `SERVICEIT_MANAGER_LAYOUT_APPLY=YES_1062_21_SHARED_MANAGER_LAYOUT`, подтверждение корпоративного администратора и зашифрованный backup до записи.
- После завершения единичной операции и сверки UI/REST администратор **отзывает временный вебхук** и удаляет одноразовый секрет из GitHub. Ежедневная работа остаётся на прежнем неадминистративном вебхуке.
- Если компания не хочет выдавать административный токен даже временно, администратор сам один раз создаёт воронку/включает поля через корпоративный интерфейс; затем запускается только безопасный readback.
