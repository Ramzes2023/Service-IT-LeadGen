# ЕИС — единый повторяемый рабочий цикл, только один источник

## Цель

Закрыть главный технический разрыв существующей ЕИС-интеграции: раньше оператор запускал скрипты **раздельно**, а новые запросы не сравнивались со всеми предыдущими успешными наблюдениями. Мы уже проверили на Windows официальный HTTPS RSS, отрицательный поисковый контроль, 4 фразы услуг 1С и фильтрацию 108 уникальных закупок; все 108 покупателей имеют признаки публичного сектора по названию. Эти закупки **не являются готовыми B2B-лидами** для Микаила, но могут быть отдельными тендерными возможностями «Сервис ИТ».

## Что работает в коде

Модуль `leadpilot/eis_daily.py` объединяет:

1. Из локального успешно прочитанного **официального** `eis_scope_*.json` извлекается исходная RSS-ссылка. Транспорт только HTTPS с полной проверкой TLS. Параметры поиска/региона не изобретаются.
2. Выполняются ровно **четыре последовательных GET** к ЕИС по ранее проверенным запросам «сопровождение 1С», «техническая поддержка 1С», «доработка 1С», «настройка 1С». Если источник возвращает 429/403/ошибку XML — нет ретраев или обходов.
3. Сохраняются четыре оригинальных JSON и общий summary в **новую** рабочую папку. `build_queue` сверяет официальные URL, SHA-идентификаторы, даты, количество, дубли и допускает только `crm_ready=false`.
4. `triage` классифицирует предмет закупки и признаки публичного заказчика, без автоматической проверки ИНН или объявления «частный/малый». Отчёты в JSON и UTF-8-SIG CSV.
5. В постоянной SQLite `eis_official_history.sqlite3` сохраняются только проверенные official notice URL. **Первый успешный запуск — исходная база, а не 108 новых лидов**. В последующие запуски сравнивается полный набор URL и выделяются **только ещё не встречавшиеся извещения** (`eis_new_since_previous.csv`). Уже виденные возвращаются в отчёт полного цикла, но не считаются новыми.
6. Конкурентные запуски блокируются lock-файлом, запись SQLite транзакционная, повреждённая RSS/смешанный batch не меняет историю; ошибки останавливают цикл с кодом 2, а не показывают фиктивный успех. Удаление устаревшего lock только после ручной проверки отсутствия активного процесса.

**Итоговые файлы** в `%LOCALAPPDATA%\ServiceIT\EIS-Daily-Operational\run-*\`: `run_summary.json`, `eis_review.json`, `eis_triage.json`, `eis_triage.csv`, `eis_new_since_previous.csv` и 4 исходных RSS JSON. История отдельно в `eis_official_history.sqlite3`.

## Как запустить

В закреплённой ветке `feat/serviceit-eis-108-candidate-legal-review-20261031`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\RUN_SERVICEIT_EIS_DAILY.ps1
```

Windows-скрипт использует существующее Python-окружение проекта, тот же предыдущий официальный JSON и постоянную папку состояния. Сначала выполняет регрессионные EIS тесты, затем 4 официальных GET и сверку состояния. Не затрагивает main и VALYQON (для безопасного запуска используйте отдельный pinned worktree).

## Что ещё требуется для честной окончательной приёмки ЕИС

1. Новый код `tests/test_eis_daily.py` добавлен в PR #30, **но первый живой запуск этой версии на Windows ещё не выполнен**. Нельзя обещать, что полный приёмочный цикл зелёный до его вывода.
2. Чтобы получать **именно свежие закупки Москвы/МО и 223-ФЗ**, оператор должен выбрать фильтры на официальном UI ЕИС и сохранить соответствующую настоящую RSS-ссылку. Сегодняшний проверенный URL был пробным `fz44=on`, без доказанного региона.
3. Пока RSS не содержит подтверждённого срока подачи и статуса процедуры, нельзя автоматически считать извещение действующей доступной закупкой. Для рабочей тендерной возможности нужен официальный номер, дата, статус, крайний срок и документы.
4. Для B2B лидов Микаилу отдельно необходимы ИНН именно покупателя, ФНС микро/малое Москва/МО, контакт, законное основание, дубли/стоп-лист и решение менеджера; **0 CRM writes и 0 ready leads**. Без разрешённого тестового Bitrix24 коннектора никакие автоматические CRM записи не выполняются.
5. Ежедневный запуск по расписанию устанавливается **только после** успешной ручной Windows-приёмки и явного действия оператора: не вносить молча новые задачи Windows на компьютер.

Таким образом, это реальный единый EIS operational workflow, а не очередной несвязанный источник. Следующий этап — **закрыть именно Windows acceptance и расписание ЕИС**. 1CLancer, B2B-Center, VALYQON не меняются.

## Важное уточнение: пустая первая выдача и планировщик Windows

Постоянная база содержит отдельную запись `operation_meta.baseline_completed`. Даже когда первый успешный RSS вернул **0** подходящих извещений, это сохраняется как успешный начальный цикл. Следующий запуск с новой закупкой корректно покажет `new_notices_since_previous_success=1`; программа не будет повторно считать его «первым запуском» и терять новизну.

`scripts/RUN_SERVICEIT_EIS_SCHEDULED.ps1` выполняет рабочий цикл без долгого набора тестов, записывает журнал и код завершения в папку состояния. `scripts/INSTALL_SERVICEIT_EIS_DAILY_TASK.ps1` регистрирует отдельную Windows Scheduled Task **только по явному вызову с `-Enable`**; время по умолчанию 09:30 локального времени оператора. В отсутствие `-Enable` не изменяется ни одна задача Windows. Для команды установки требуется **предварительно успешно подтверждённая ручная приёмка** изолированной версии.

Добавлены регрессионные тесты первого запуска с нулём, одного нового извещения после пустого первого запуска, повторной стабильной выборки, блокировки параллельных запусков, отказа после 429 без изменения SQLite, безопасных CLI-выходов при успехе и ошибке. Никакие показатели нового кода не считаются подтверждёнными до результата на Windows.
