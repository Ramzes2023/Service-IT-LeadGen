# Автоматический предварительный Lead Score при отсутствии ФНС

## Зачем это нужно

По решению владельца 04.11.2026 отсутствие официальных данных ФНС **НЕ должно тормозить предварительную оценку**. Все будущие реальные карточки смарт-процесса `entityTypeId=1062 / categoryId=21`, созданные после cutover, получают числовой **предварительный приоритет сигнала 0–100**. Число получено из детерминированного triage `serviceit_three_signal_triage`, а не из GigaChat-confidence, финансовых данных или FNS: это не подтверждённый рейтинг покупателя.

### Поля при успешной записи

- `UF_CRM_13_SVCIT_LEAD_SCORE`: число 0–100 (ранжирование предварительного сигнала).
- `UF_CRM_13_SVCIT_SCORE_VERSION`: `svc-prelim-v1-FNS-UNVERIFIED` — обязательный машинный маркер неполного доказательства.
- `UF_CRM_13_SVCIT_AI_SCORE_BADGE`: `🔎 65/100 · ПРЕДВАРИТЕЛЬНО · ФНС: НЕ ПРОВЕРЕНА · Дубли: ... · STOP: НЕ НАСТРОЕН · Контакт: НЕ РАЗРЕШЁН`. Значение 65 — только пример, не реальная карточка. Пустой или неуспешный ФНС НЕ является основанием скрывать предварительный балл.

Перед записью существуют девять заполненных AI-полей менеджера; если они ещё не заполнены, Score-робот повторит проверку в следующем цикле. Job `.github/workflows/serviceit-stage4-prelim-score-live.yml` с расписанием каждые 10 минут запускается только с тем же корпоративным вебхуком и включёнными существующими флагами обработки; отдельно может быть вызван точной owner-командой `SERVICEIT_STAGE4_PRELIM_SCORE_LIVE_ONCE_V1` в GitHub Issue #148. Учитываются только **новые** реальные записи, никаких демонстрационных и исторических (3,7).

### Дубли

- При валидном ИНН проверяются **все доступные страницы** по точному ИНН текущего смарт-процесса и реквизитов CRM, в том числе существующих компаний/контактов. Найденное совпадение запрещает запись нового приоритета (HOLD).
- При недоступном списке или недостатке прав ставится `Дубли: НЕ ПРОВЕРЕНЫ`; предварительная оценка всё равно возможна, но НЕТ разрешения на контакт.
- При отсутствующем/невалидном ИНН ставится `Дубли: ИНН НЕТ`; балл относится только к **сигналу**, не к проверенной компании.
- Даже после просмотра всех страниц нельзя утверждать, что вебхук видит скрытые записи всей компании.

### Безопасная запись и переход к финальному Score

Выделенный отдельный зашифрованный одноразовый журнал (GitHub CAS) создаётся **до** `crm.item.update`; checkpoint включает ожидаемые 3 значения. После UPDATE требуется `crm.item.get` и совпадение всех 3 полей, плюс сохранность остальных полей. Неизвестный исход HTTP не повторяется автоматически. Журнал не содержит открытых данных компаний и не выдаёт в лог ИНН, названия, клиента, ссылки или webhook.

**STOP-лист отложен** до решения компании; его отсутствие не приравнивается к CLEAR. Не создавать задачи и не начинать общение с компанией на основании предварительного score. Полный девятиэтапный Stage4 verifier и задачи менеджерам остаются отдельными контурами. Конечный VERIFIED Score может быть записан только по **девяти подписанным независимым корпоративным подтверждениям**. Безопасное повышение предварительного значения подключено: полноценный Stage4 writer умеет заменить **только наш собственный точно совпадающий** набор версии `svc-prelim-v1-FNS-UNVERIFIED`, числа и сформированного системой бейджа. Любое ручное изменение, другой Score или поддельная предварительная метка блокируют обновление. Переход также требует актуальный подписанный CRM before-image, пустой корпоративный STOP_REASON, доступную проверку дублей и успешное точное чтение после записи. Без официальной ФНС и остальных доказательств повышения НЕ происходит.

### Общий Канбан

Администратор один раз должен включить в карточке просмотра поля `AI — цветной приоритет` (важнее) и `Lead Score`, а также `AI — краткий вывод`; затем новая обработанная карточка покажет число и статус ФНС. Сам общий layout текущим вебхуком 1615 изменить нельзя (не администратор). Поля CRM уже существуют; новые значения пишет существующий корпоративный webhook при реальном поступлении.

## Доказательство

PR и CI являются технической подготовкой; окончательное live-E2E подтверждение требует **хотя бы одной новой реальной карточки с readback всех трёх полей**. Если при ручном запуске `candidates=0`, писать «Score уже проверен на реальной компании» нельзя.
