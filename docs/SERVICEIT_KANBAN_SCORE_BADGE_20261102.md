# Канбан: цветной Score по требованиям Микаила — этап 1

Код готовится отдельно от завершённого GigaChat/Bitrix24 Cockpit. Значения `Lead Score`, версия скоринга, поле GigaChat, задача №26163, название DEMO, стадия и старый one-shot ledger **не меняются**.

## Цель дизайна

Короткий **текстовый** индикатор в превью канбан-карточки, а не раскраска фоновой плитки:

- 🟢 `90/100 — высокий приоритет проверки` (80–100)
- 🟡 `65/100 — средний приоритет проверки` (60–79)
- 🔴 `35/100 — низкий приоритет проверки` (0–59)

Точные границы: скоринговая шкала ТЗ Микаила выделяет 80–100 высокий, 60–79 средний, 40–59 прогрев, 0–39 отложить. В 3-цветном представлении последние два интервала визуально объединены в красный. **Ни один цвет не означает разрешения связываться с компанией**: подтверждение источника, отсутствие стоп-листа, дубли, законное основание и решение менеджера нужны отдельно.

## Как устроена безопасная автоматизация

`leadpilot/serviceit_kanban_score_badge.py` и `scripts/RUN_SERVICEIT_KANBAN_SCORE_BADGE.ps1`.

- OFFLINE — локальная демонстрация цветов; нет вебхука и сетевых запросов.
- `-InspectLive` — только чтение Bitrix24. Подтверждение точного `entityTypeId=1062`, `typeId=13`, `categoryId=21`, точной DEMO #3, сохранённой версии скоринга, значения 90/100 и существующего полного GigaChat-отчёта. Проверяется, создано ли поле с кодом `UF_CRM_13_SVCIT_AI_SCORE_BADGE` и нужно ли заполнять значение.
- Только после отдельной явной команды `-InspectLive -ApplyDemo -ConfirmDemoOnly` — создать одно пользовательское строковое поле `AI — цветной приоритет` в `CRM_13`, если оно не существует, и записать **только это поле** в элемент №3.
- Каждый write требует отдельной устойчивой reservation, резервной копии и readback. При неопределённом исходе **никаких повторов**, сохранённый журнал `%LOCALAPPDATA%\ServiceIT\Kanban-Score-Badge-v1\cockpit-report-v1.sqlite3` не удалять и не переносить ради обхода защиты.
- Не меняются глобальные представления CRM, роботы, задачи, шаблоны, основной бизнес-процесс, сообщения клиентам и пользовательские настройки GigaChat.
- Добавлен mock-only CI + Windows PowerShell 5.1 тест с безопасным вводом SecureString.

## Важное ограничение: показ на плитке Канбана

REST может создать поле и заполнить значение, **но это НЕ заставляет Битрикс24 вывести поле на плитке канбана**. Официальная инструкция (июль 2026): ⚙ → Настройка канбана → Настроить карточку просмотра → включить поле `AI — цветной приоритет`. Каждый пользователь может сделать это для себя; администратор может настроить общую форму просмотра. Документированного публичного REST для назначения набора полей канбана через вебхук нет.

Поэтому результаты оператора возвращают `kanban_display_configured: false`, даже при успешной записи поля. Это не скрытая ошибка, а отдельный UI-шаг. Последующее браузерное автоматизированное действие потребует авторизованной браузерной сессии, проверенных конкретных элементов UI и отдельного opt-in; не должно публиковать токены, использовать чужие сессии или угадывать скрытые API.

## Операция оператора

Из доверенного worktree с явно выбранным Python:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\RUN_SERVICEIT_KANBAN_SCORE_BADGE.ps1 -PythonPath $Python -InspectLive
```

При безопасном предпросмотре отобразится `KANBAN_BADGE_READONLY_PREVIEW` с ожидаемым `🟢 90/100`. Для последующего явного одноразового применения:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\RUN_SERVICEIT_KANBAN_SCORE_BADGE.ps1 -PythonPath $Python -InspectLive -ApplyDemo -ConfirmDemoOnly
```

Ни одна из этих команд не меняет макет Канбана. Если после apply появится `BADGE_BLOCKED_OR_UNCERTAIN`, повторять apply нельзя: первым делом read-only аудит Bitrix и локального журнала. Если `KANBAN_BADGE_DEMO_VERIFIED`, значение введено и readback подтверждён, но **саму плитку** нужно отдельно проверить в браузере.
