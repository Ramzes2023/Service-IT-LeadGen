# Единый приёмник новых карточек Bitrix24 1062/21

## Почему новая карточка B2B-Center была пустой

Ранее реальное уведомление B2B-Center попадало через Github Actions b2b-gmail-to-bitrix-hold.yml, и этот писатель создавал HOLD-карточку только с исходными полями. Демо GigaChat №3 было одноразовым и не реагировало на новые элементы.

После PR #71 новые карточки B2B-Center автоматически получают девять предварительных полей анализа с честным статусом NOT_RUN_SOURCE_UNVERIFIED. Это ещё не GigaChat и не Score — закупка, заказчик и ИНН не подтверждены.

## Новый компонент

leadpilot/serviceit_bitrix_event_receiver.py: POST /integrations/serviceit/bitrix24/new-card.

Принимает ONCRMDYNAMICITEMADD и ONCRMDYNAMICITEMADD_1062 (если событие с суффиксом поддерживает конкретный Bitrix24). Поддерживает JSON и application/x-www-form-urlencoded.

Защита:
- обязательный auth.application_token, сравнение в постоянное время, отдельная секретная переменная окружения SERVICEIT_BITRIX_APPLICATION_TOKEN;
- точный auth.domain=serviseit.bitrix24.ru, data.FIELDS.ENTITY_TYPE_ID=1062 и допустимый положительный ID;
- входящий запрос до 16 KiB, отбрасывание остальных процессов;
- SQLite SERVICEIT_BITRIX_EVENT_QUEUE_DB с уникальным ключом на каждую новую карточку;
- очередь хранит только item_id, entity_type_id, время и PENDING_SOURCE_CHECK; без токенов, текста закупки, персональных данных и URL;
- повторное событие не порождает дубль.

Это НЕ production-обработчик анализа: он не подписывает event.bind, не вызывает crm.item.get/update, не запускает GigaChat и не меняет существующие карточки. Прототип не развёрнут на корпоративном сервере. Он только устойчиво принимает новые ID.

## Что нужно до полностью автоматического AI на ВСЕХ карточках

1. Развернуть закрытый HTTPS-адрес на согласованном сервере и безопасно подключить отдельный application_token (входящий REST webhook не заменяет его). Для исходящего вебхука нужна отдельная проверка формата аутентификации.
2. Зарегистрировать событие создания смарт-процесса 1062 с согласия администратора, проверить реальное получение одного тестового события и дедупликацию. Не регистрировать неподготовленный endpoint.
3. Написать read-only consumer по элементу: crm.item.get с точным entityTypeId=1062 и categoryId=21. Прежде чем оценивать, проверять источник, покупателя, ИНН/ФНС, дату, CRM-клиентов, дубли, стоп-лист и законное основание обработки.
4. Только на допустимом подтверждённом тексте запускать детерминированный Score и GigaChat (модель не назначает Score). Заполнить девять AI-полей и Score/version/badge.
5. Выполнять однократную разрешённую запись по одному элементу с полным readback, новой независимой idempotency/outbox защитой, без изменения стадий и задач. Никаких повторов при UNCERTAIN, никогда не сбрасывать старые журналы.
6. Отдельным контролируемым backfill обработать существующие карточки, включая B2B-Center №4661617, после read-only квалификации. Это не должно создавать второй элемент CRM.

Без этих условий нельзя заявлять, что настоящий GigaChat автоматически обрабатывает все новые карточки на портале.
