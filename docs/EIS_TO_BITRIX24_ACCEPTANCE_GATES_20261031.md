# ЕИС → Битрикс24: точные условия готовности по письму Микаила и ТЗ v3.0

## Откуда критерии

Из письма Микаила **30.10.2026** («ТЗ Лидогенерация») и приложения **«ТЗ_система_лидогенерации_Сервис_ИТ_итоговое.docx»**, версия 3.0, август 2026. Первое направление: **сопровождение 1С, микро/малые компании Москвы и Московской области**. Требуется не список закупок, а **обоснованный сигнал потребности конкретной компании → проверка → подтверждённый контакт → Lead Score → Битрикс24 → задача менеджеру**. Дополнительные требования: исключать текущих клиентов, дубли, стоп-лист и нерелевантные компании; не создавать рекламные робозвонки и не писать с корпоративных сервисных аккаунтов.

## Фактическая техническая готовность ЕИС

Два подтверждённых реальных ручных Windows запуска: **228** и **236** зелёных тестов, четыре официальных RSS GET, локальная SQLite и автоматическая дедупликация. Задача Windows **ServiceIT-EIS-Official-Research-Only** установлена на 09:30 по локальному времени Windows, после исправления блокировки питания `Queued → Ready`, пробный scheduled run `EIS_REPAIR_PROBE=PASS`. 108 уникальных извещений и 108 текстовых признаков публичных покупателей. Это **рабочий исследовательский источник тендеров**, не готовые 108 коммерческих лидов.

## Новая контролируемая граница ЕИС → CRM

Модуль `leadpilot/eis_bitrix_readiness.py` проверяет **реальную локальную историю**, не синтетический счётчик: сверяет последнюю SQLite/CSV/JSON через `eis_daily_health.verify`. По запросу может учитывать **отдельный** read-only buyer/FNS audit `eis_buyer_review`, manual manager queue `eis_manager_queue` и результат `eis_bitrix_sandbox` для изолированного тестового смарт-процесса. Источники, переданные оператором, *не дают автоматического разрешения писать в CRM*: всегда `crm_write_enabled=false`, `crm_ready=0`, `outbound_messages=NO`. Результат показывает измеримые блокеры, даже если RSS-транспорт уже PASS.

```powershell
.\.venv\Scripts\python.exe -m leadpilot.eis_bitrix_readiness --state-dir "$env:LOCALAPPDATA\ServiceIT\EIS-Daily-Operational"
```

Без реального тестового Битрикс-портала этот модуль **не вызывает никакие методы Bitrix24 и не требует/печатает webhook**. Планы CRM в пользовательском документе не означают, что портал/токены/права уже предоставлены. Предположение о «лёгком немедленном переносе всех 108 извещений» ошибочно: у настоящего покупателя должен быть подтверждённый ИНН и коммерческая квалификация.

## Шлюзы до фактической CRM интеграции

1. **Оригинальные карточки** `zakupki.gov.ru`: проверить статус **открытого** приёма, действительный дедлайн/часовой пояс, документацию и предмет, номер, заказчика, регион и каналы правомерного участия; не пытаться выдумывать закрытый API/параметры.
2. **Точная юридическая категория заказчика**: если это бюджетное учреждение/ведомство, тендер может быть релевантен для участия в госзакупках ООО «Сервис ИТ», но **не является** целевым B2B-лидом микро/малого коммерческого покупателя. Это два отдельных потока. Сверять заказчика по точному ИНН и официальной ФНС `rmsp.nalog.ru`; не подменять покупателя организатором/поставщиком и не считать МСП-ограничения для поставщика размером покупателя.
3. **Менеджерская квалификация**: есть ли подтверждённая потребность во *внешнем* сопровождении 1С, свежесть, контактная роль/корпоративный канал, актуальность, право контакта, стоп-лист по каналам, настоящий `Lead Score`, версия и объяснение, решение Микаила.
4. **Схема Битрикс24**: доступ от ООО «Сервис ИТ» к выделенному тестовому порталу/смарт-процессу, реальные `entityTypeId`, `categoryId`, `stageId`, custom `ufCrm...` для ИНН, источник, ID сигнала, дата, TTL, статус, история. Не делать запись стандартного Lead в чужую продажную воронку: категория сделки не изолирует Лид.
5. **Read-only REST acceptance**: `crm.category.list`, `crm.item.fields`, `crm.item.list` в выделенном смарт-процессе с выключенными роботами, проверка существующих клиентов и дублей/стоп-листа; история + сигнал как отдельная запись без перезаписи предыдущего сигнала.
6. **Тест записи**: только после явного согласия владельца и с обезличенной синтетической записью в изолированном портале; контроль повторного импорта (idempotency), удаление тестовых данных согласно разрешению, журнал ошибок и контроль запрета рассылок. Реальные данные без подтверждённых шлюзов — **NO-GO**.

Официальная документация Битрикс24: https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html ; https://apidocs.bitrix24.ru/api-reference/crm/universal/user-defined-object-types/index . Методы `crm.item.add` реально создают элементы, поэтому текущий путь должен оставаться **только для чтения**.

## Граница планирования

Период **4–6 недель из ТЗ** — длительность **пилота всей системы после запуска**, а не гарантированная дата сдачи ЕИС и не срок допуска к Битрикс24. Календарный срок зависит от официальных данных, согласованной модели B2B/госзакупок, корпоративного API доступа, полномочий и контрольного теста. Пропуск этих шагов нельзя компенсировать зелёными локальными pytest.

ЕИС остаётся **единственным источником, который меняем в этой ветке**. Основная ветка, другие торговые площадки, VALYQON и живой Битрикс24 не изменяются.
