# Сервис ИТ — AI LeadGen: общая архитектура + демонстрация в корпоративном Bitrix24

**Рабочая поверхность:** смарт-процесс «Сервис ИТ — AI-сигналы», `entityTypeId=1062`, `categoryId=21`. Существующая `DEMO-ITREQ-001` — карточка №3, связанная задача — №26163, исполнитель из `profile` существующего разрешённого вебхука.

Это **общий модуль квалификации и подготовки**, не новая система, привязанная навечно к одной карточке. Текущая единственная разрешённая **реальная запись** ограничена четырьмя заранее существующими полями карточки №3 для учебной демонстрации. Промышленный адаптер реальных компаний **не включён**.

## Общий конвейер (не зависит от ID карточки)

`leadpilot/serviceit_ai_lead_engine.py`:

`компания + несколько сигналов с источником/датой → нормализация → контроль дублей сигнала → срок актуальности → 7 независимых проверок → score_company (версия правил) → гипотеза AI отдельно от фактов → понятный бриф менеджеру → план элемента смарт-процесса 1062`.

Выполняется для любых переданных разрешённых данных, **без REST-вызовов и внешней коммуникации**. Прежние `core.ingest`, `core.suppress`, `core.qualify` и `workflow_ops` обеспечивают локальные стойкие записи/стоп-фильтры/симуляции. Новый план `plan_serviceit_ai_signals()` показывает, что именно направлялось бы в существующий смарт-процесс. Он **ничего не записывает**, и не превращает отсутствие проверки клиентской базы в разрешение.

Для каждой реальной компании обязательны явно независимо проверенные признаки `VERIFIED`: официальный статус компании, источник доказательства, отсутствие у компании статуса действующего клиента, CRM-дедупликация, стоп-лист, допустимое основание коммуникации и подтверждённый корпоративный контакт. Если хоть один `UNKNOWN` или `BLOCKED`, **CRM-передача блокируется**. Даже после всех проверок менеджер должен принять решение: AI и score не дают автоматического разрешения звонить.

Lead Score **всегда детерминированный** и версионный: `mvp-2026-10-v1`. AI возвращает только `AI_hypothesis`; текст источника и гипотеза хранятся и помечаются отдельно, модель не устанавливает score и не выдумывает контакты.

## Реальная корпоративная DEMO-интеграция

`leadpilot/bitrix_1062_demo_qualification.py` использует **тот же общий движок**, но принимает только строго проверенную синтетическую карточку 1062/21/3 с фиктивным ИНН, источником `synthetic-fixture`, отсутствием контактов, правильным idempotency и всеми 16 исходными UF. Полученная на 1 ноября учебная оценка — **90/100**, она не отражает реальную вероятность договора.

По умолчанию:
- защищённый `crm.item.get` и проверка метаданных + `crm.item.fields`, расчёт брифа;
- никаких изменений и вызовов AI без отдельного флага.

При явном `-ApplyDemo`:
- один `crm.item.update` на **те же** 1062/21/3;
- **только** `UF_CRM_13_SVCIT_LEAD_SCORE`, `...SCORE_VERSION`, `...MANAGER_NEXT_ACTION`, `...STOP_REASON`;
- никаких новых задач (№26163 уже существует), контактов, компаний, стадий, исходящих сообщений и звонков;
- локальная durable SQLite-резервация **до POST**, последующее независимое `crm.item.get` и повторная metadata read-only проверка; при сбое — запрет слепого повтора.

AI-режим `-UseExistingGigaChat` подхватывает существующий личный ключ из *известных локальных* конфигураций VALYQON или процесса Windows, не передаёт его в чат/GitHub, отправляет модели лишь одну **заранее написанную вымышленную фразу**. Если модель дала непроверенную цитату или низкое качество, запись в CRM не проводится. AI-текст обозначен «гипотеза»; не становится фактом и не меняет 90/100.

## Однокомандный Windows-оператор

Из закреплённой ветки/коммита после CI (создан только код, не нужно никакой настройки Михаила):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/RUN_SERVICEIT_AI_LEAD_GENERAL_DEMO.ps1 -ApplyDemo -UseExistingGigaChat
```

Скрипт автоматически пытается использовать существующий локальный токен GigaChat, затем **скрыто** запрашивает корпоративный webhook. Новую учётную запись AI создавать не нужно. Может появиться внутреннее уведомление об изменении DEMO-карточки.

Если локального ключа нет, запуск `-UseExistingGigaChat` остановится **без CRM-записи**. Тогда можно отдельно провести демонстрацию только детерминированного Lead Score, запустив `-ApplyDemo` без AI; в карточке будет явно написано, что AI не запускался.

Вывод `DEMO_CRM_QUALIFICATION_VERIFIED` — единственное подтверждение настоящего чтения после записи. Вывод `DEMO_PREVIEW_READY` — только просмотр. Вывод `BLOCKED_OR_UNCERTAIN` — **не повторять -ApplyDemo до проверки SQLite и карточки**.

## Оставшиеся условия до реального запуска

1. Согласованное ограниченное чтение **реальной** CRM клиентской базы, действующих/потерянных клиентов и стоп-листов; проверка дублей по ИНН/телефону/email должна работать в обе стороны и проверять права текущего вебхука. Это отдельное разрешение заказчика и отдельный код; сейчас `NOT_VERIFIED`.
2. Сопоставление входных реальных сигналов с подтверждёнными ФНС/сайтами и корпоративными контактами, договорённость о правовых основаниях контакта.
3. Утверждение manager-review, правил RBAC, обработки отказа, журналов и SLA до разрешения реальной записи.
4. Отдельная интеграция входящих ботов/телефонии, аналитика до договора/выручки — следующий релиз по ТЗ.

**Нет производства:** даже если код PR успешно прошёл GitHub Actions, это не подтверждает работу GigaChat и не запускает серверный worker. Вебхук и корпоративная информация хранятся только локально и **не пересылаются в чат**.

Официальный Bitrix: [crm.item.update](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-update.html), [crm.item.fields](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-fields.html).
