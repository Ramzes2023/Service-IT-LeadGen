# Полная карточка для каждого нового сигнала — общий AI/CRM create-intent

## Почему новые карточки пустые

До этого момента интеграция GigaChat была **однократной и привязанной к DEMO item №3**. Наличие новых полей и успешная проверка схемы не запускают AI на каждом новом элементе. PR #68 даёт лишь безопасный офлайн-расчёт пакетного Score и цвета, но не регистрирует событий Bitrix24 и не создаёт новых элементов. Новый элемент, созданный другим источником/оператором, поэтому не заполняется автоматически нашим кодом.

Для **реальной автоматизации** нужен запуск обработки после появления карточки: официальный `onCrmDynamicItemAdd` (только `data.FIELDS.ENTITY_TYPE_ID=1062` и разрешённая `categoryId=21`), а также `onCrmDynamicItemUpdate` для изменений данных источника; защищённый серверный обработчик, очередь, readback, dedupe/version gate. Обработчик должен извлекать ИНН, исходную ссылку и доказательство, делать независимые проверки клиентов/дублей/права контакта, запускать GigaChat с ограничениями privacy и проверкой точной цитаты, затем формировать поля и делать одну авторизованную запись с idempotency и подтверждённым readback. **Не регистрировать неподготовленное событие с неконтролируемым webhook.**

Документация: https://apidocs.bitrix24.ru/api-reference/crm/universal/events/on-crm-dynamic-item-add.html.

## Что теперь есть в коде (ещё без live writes)

- `leadpilot/serviceit_source_batch_pipeline.assess_source_batch`: берёт пакет кандидатов, группирует по ИНН, исключает точные дубли и конфликтные данные, выдаёт один внутренний `assess_lead` на компанию.
- `leadpilot/serviceit_all_lead_crm_create_intents.build_all_lead_intents`: собирает **по одному полному create-intent на каждую уникальную компанию**, с `entityTypeId=1062`, `categoryId=21`, фиксированной стадией `DT1062_21:NEW`, отдельным idempotency hash, всеми 16 исходными полями, Score, версией, 🟢/🟡/🔴 и **девятью AI-полями** (всего 29 полей с title/stage/category). Это лишь `params_NOT_SENT`, `can_execute=false`, без реальной записи.
- `serviceit_ai_report.build_report` проверяет Score, факторы и точную цитату, строит краткий вывод, ограничения, чек-лист и полный отчёт. При отсутствии подтверждённого вызова GigaChat текст имеет честный статус `AI_STATUS=NOT_RUN`, а не выдуманную гипотезу AI.
- `ai_by_fingerprint` — явно инъецируемый готовый и валидированный результат GigaChat, который может передать **будущий** согласованный рабочий обработчик; тогда поле `AI_STATUS=HYPOTHESIS_UNVERIFIED`. GigaChat в этом PR **не вызывается автоматически**. AI не меняет детерминированный Score.
- Две старые непроверенные операции записи badge на DEMO №3 `UNCERTAIN` остаются без изменения; не повторять и не обходить.
- CLI и Windows PowerShell `scripts/RUN_SERVICEIT_ALL_LEAD_CRM_CREATE_PREVIEW.ps1` выводят только обобщённую оценку/статусы, не раскрывают реальные ИНН, источник, контакт, вебхук, содержимое полного AI-отчёта.

## Почему нельзя прямо сейчас объявить «AI автоматически для всех»

На корпоративном портале есть подтверждённые 9 AI-полей и 3 поля скоринга; но нет доказанного server-side события, провайдера для **каждого** нового источника, доверенных проверок CRM клиента/стоп-листа, разрешённой очереди записи и массового live end-to-end. Сырые входные сообщения могут быть непроверенными или содержать персональные данные. Даже `HOLD_UNVERIFIED` может иметь зелёный Score; цвет означает приоритет проверки, а не готовность к звонку или право контакта.

Пока PR формирует **полные безопасные параметры будущих карточек** в одном месте и тестирует через `httpx.MockTransport` создание двух элементов, чтение всех полей и отказ при дублированном ключе, не обращаясь к Bitrix.

## Перед боевым включением

1. Подтвердить источник только для CRM `1062/21` и наличие подписанного корректного обработчика `onCrmDynamicItemAdd`, определить текущую программу, создающую «новую карточку», не переписывать её вслепую. Приложение или автоматизацию нужно проверить с согласия администратора.
2. Проверить, какие поля реально заполняет **новая** карточка после создания (только read-only), прежде чем запускать GigaChat: источник, URL, оригинальный текст, дата, тип, ИНН и признаки demo/test.
3. Подключить защищённый обработчик с кэшем и idempotency по entity/id/score_version/source fingerprint, безопасным GigaChat, ограничением бюджета и AI и без запуска при пустом доказательстве.
4. Установить write-gate и readback по всем новым 9+3 полям, один controlled request, ноль повторов при неопределённом исходе, собственные журналы. Не очищать старые `UNCERTAIN`.
5. Проверить под аккаунтом Микаила общую форму Канбана, а не только локальную карточку.
