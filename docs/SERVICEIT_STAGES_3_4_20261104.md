# «Сервис ИТ»: этапы 3 и 4 — контрольная точка 04.11.2026

## Граница работ
Никаких изменений Gmail V9, источников, входящей очереди, Битрикс-сценариев источников и действующей воронки поддержки. Только задачи/Канбан и квалификация/Score.

## Этап 3: задачи менеджера и оформление
- Уже существует защищённый план общего оформления карточки 1062/21. Последний реальный read-only аудит: PREVIEW_ONLY, ADDED=1, CRM_WRITES=0. До разрешения корпоративного администратора layout НЕ менять. Отображение плитки Канбана под аккаунтом менеджера отдельно не проверено.
- Новый модуль leadpilot/serviceit_manager_task_readonly_v2.py выполняет исключительно чтение: user.get (поиск кандидата), crm.enum.ownertype (префикс привязки), tasks.task.list (только привязка исторической демонстрационной задачи к #3). ФИО, контактные данные, пользовательские ID и заголовки задач не выводятся.
- Совпадение ФИО — только кандидат, не подтверждённое разрешение назначать задачи. Даже успешная проверка привязки #3 не доказывает отсутствие дублей у будущих новых карточек. tasks.task.add не вызывается.
- Workflow serviceit-manager-task-readonly-v2.yml можно запустить только авторизованным комментарием SERVICEIT_STAGE3_MANAGER_TASK_READONLY_V2 от владельца в Issue #74. Права: contents=read и issues=read.

Для разрешения реальной постановки задач всё ещё нужны утверждённый corporate manager user ID, права task, точная дедупликация новой карточки, неизменяемый журнал однократной попытки, readback и разрешение ответственного компании. Если ответ REST после записи неопределённый, повторять запись нельзя.

## Этап 4: проверка доказательств и формальный Score
- Существующий детерминированный движок assess_lead() нельзя выдавать за формальную квалификацию, когда проверки подставлены из незаверенного словаря.
- Новый модуль serviceit_qualification_proof_v2.py: девять независимых корпоративных подтверждений с origin, finding=CLEAR, временем до 60 минут, ИНН и SHA-256 доказательства. Они должны приходить в HMAC-подписанном документе, привязанном к конкретной новой карточке 1062/21 и before_hash. Без действительной подписи и всех девяти результатов: HOLD, formal_lead_score=None.
- Проверки: ФНС/реестр компании; первоисточник; наличие действующего клиента; глобальный CRM dedup; общий STOP-лист; законное основание; проверенный официальный контакт; ФНС-МСП и регион; правила менеджера.
- При успешном подтверждении применяется версия существующей детерминированной формулы. Итог всё равно требует решения менеджера. Вакансия остаётся кадровым сигналом без разрешения рекламного контакта.
- Чтение crm.requisite.list по контрольному ИНН способно обнаружить видимый CRM-реквизит, но отсутствие найденной записи НЕ доказывает глобальную пустоту CRM: webhooks видят только разрешённые объекты. Поэтому false negative не даёт VERIFIED.

**Предел завершённости:** здесь построена и тестируется безопасная граница доверия, НЕ подключён сам корпоративный верификатор (ФНС, полный CRM, STOP, право контакта). Новый проверяющий модуль пока не включён в производственный enrichment worker: это отдельный разрешённый cutover после корпоративной интеграции. Никаких новых реальных лидов/задач/CRM записей этим PR не создано.
